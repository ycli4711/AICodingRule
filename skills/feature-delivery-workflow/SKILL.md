# 通用功能交付

在一个主会话中，把需求推进为逐功能交付。服务端与各客户端可位于同一或不同仓库；只安排实际相关参与方。通用规则留在 Skill，业务、接口、工程路径和验证结果放在本次运行记录。

简单问答、明确的局部文案或样式修改沿用普通处理，不开启完整流程。纯服务任务可使用本流程，但界面设计和视觉验收标明不适用。

## 按当前阶段行动

先判断用户要的是讨论、方案、实施、验收还是恢复，沿用已完成且仍有效的记录。

| 当前需要 | 行动与参考 |
| --- | --- |
| 首次进入或项目不明 | 核实目标、项目绑定与工具能力，读取 [协调规则](references/coordination.md) |
| 定义需求、设计接口或制定计划 | 按阶段顺序读取 [需求、接口与实施计划](references/feature-design.md)，不提前合并确认 |
| 开发、交接、阻塞或恢复 | 按有效授权推进，读取 [协调规则](references/coordination.md)；阻塞时核实解除步骤，不只留下“等待环境就绪” |
| 首次记录或更新进度 | 按 [运行记录](references/run-records.md) 保留必要状态和证据 |
| 联调、验收或交付 | 读取 [验收规则](references/acceptance.md)，按端给出实际结论 |

只读取当前阶段相关参考。没有原型可结合现有产品讨论交互，不要求用户先准备完整设计。

开发时按 [执行效率](references/coordination.md#执行效率) 提前核查环境、及时交接契约并共享有效验证结果；收尾按 [收敛规则](references/acceptance.md#收敛规则) 判断完成条件。提速不减少必要审核、测试或项目强制检查。

## 按阶段调用角色 Skill

主控负责范围、阶段确认、授权、依赖、并行调度和最终交付；专业判断由下列角色规则约束。进入相应阶段时读取对应 Skill，不只在任务里写角色名称，不一次加载全部角色。

| 阶段 | 角色及输入 | 交回主控的结果 |
| --- | --- | --- |
| 需求分析、接口及架构设计 | [需求与架构设计](../requirements-architecture/SKILL.md)：目标、资料、仓库、当前阶段和有效确认 | 可审查需求或设计、必要结构及理由、接口/数据/前端接入、决策与缺口 |
| 获授权后的开发与修复 | [开发实现](../project-implementation/SKILL.md)：有效方案、授权、规范路径、修改边界与基线 | 实际代码变化、规范与行为验证、依赖就绪范围及剩余项 |
| 实现后审核、修复复核 | [代码审核](../project-code-review/SKILL.md)：需求与规范、实际差异、基线和验证证据 | 有依据的问题、影响和修复方向；复核后的关闭状态 |
| 制定验证范围、联调与功能验收、缺陷复测 | [测试与验证](../project-test-validation/SKILL.md)：已确认需求/契约、测试规范、构建版本、环境及操作授权 | 分层验证结果、缺陷复现证据、修复复测及未覆盖项 |

实施计划仍由主控按设计参考制定，不额外创造“计划角色”。角色 Skill 不等于必须启动新代理：简单任务由主控按对应规则执行；可独立的开发任务按协调规则并行，复杂或重要改动在工具和授权允许时优先由不同执行者审核。无独立审核者时明确为自查，不伪称独立审核。

分派时附角色 Skill 的实际路径，执行者先读角色规则再读所属仓库规范。子任务不回调主控工作流或递归组建角色团队；每个角色只返回本阶段结果，主控核实后交接。角色切换不新增审批，不重做有效确认；角色文件不可用时说明限制，按已读取的适用规则继续独立且已授权的工作，不声称已调用缺失角色。

测试角色可在实施计划阶段准备验证范围；实际测试按有效授权与环境条件执行。开发完成必要自测后，代码审核与测试验证在版本明确、文件和测试资源不冲突时可并行；修复后分别复核代码和复测行为，再交主控核对交付。三类证据不相互替代，也不要求简单任务额外启动测试代理或重复有效检查。

## 页面审查与聊天反馈

生成文档前读取 [运行记录](references/run-records.md) 的组织规则。原型导航目录保留已核实的名称、层级和顺序，到页面为止；内容按目标连贯、可独立理解和确认的用户场景组织。多个独立场景混在一起影响审查时，增加明确标注的审查分组，不将分组冒充原型菜单，也不按 URL、界面容器或预设页面类型机械拆分。每次审查回复简短说明当前阶段、当前审查项及链接、下一步，再列必要问题与修改结果，不粘贴整页或全系统说明。用户直接回复、圈图或聊天文字批注即可反馈，主控负责定位和记录；Markdown 文件本身不具备批注能力。

跨阶段前说明目标阶段、具体范围和进入依据。“继续”不能直接当成需求确认、接口确认或跨阶段确认；应结合此前明确展示的待确认事项与下一步判断。未说明去向或存在歧义时，继续当前阶段的整理与核查，并澄清实际缺失的确认；不先生成下一阶段产物再补确认。已明确取得且仍有效的确认和授权不重复索取，具体规则见 [运行记录](references/run-records.md)。

## 推进顺序

1. **绑定项目**：从有依据的路径和宿主项目记录识别各端；展示绑定与缺口，不从截图名称推断路径。
2. **拆分需求**：列出所有功能、依赖与当前项。按可验证的业务结果拆分，默认一个活动功能。
3. **需求定义与确认**：按当前审查项用业务语言说明使用者、目标、操作与结果、字段与校验、状态与权限规则、异常反馈和验收标准，并关联来源页面或业务能力。交互属于需求；关键缺口闭合并获用户确认后，才进入该范围的接口设计。
4. **接口及接口逻辑设计与确认**：基于已确认需求，开头用简短文案突出接口变化、阻塞问题和待决策项，再按接口集中说明契约与核心业务逻辑。内容边界、去重和阅读顺序遵循 [需求、接口与实施计划](references/feature-design.md)，不在接口正文铺开实施安排或核查记录。用户确认该范围的接口及逻辑后，才制定实施计划。
5. **制定实施计划并取得实施授权**：引用已确认的需求和接口版本，安排相关端任务、依赖、修改范围、实施步骤与验证方式。计划可审查后取得具体实施确认，再开始开发；需求或接口确认本身不等于业务写入授权。
6. **开发与联调**：实施确认后、写代码前，按 [分支与运行环境](references/coordination.md#分支与运行环境) 创建独立分支和 worktree；独立端口启动，复用已确认的共享开发数据库和 Redis。区分开发与联调依赖，满足条件的前后端独立任务优先并行实施；只等待真正依赖的部分，已就绪部分及时真实联调。
7. **审核与验收**：调用代码审核与测试验证角色，按相关端分别核查代码和实际行为；修复范围内问题，完成必要复核与复测，再核对证据。
8. **交付与继续**：对照当前功能核对完成条件，不能只列遗留项就结束。已授权且可执行的剩余必要工作继续做；需新增授权的按 [阻塞处理](references/coordination.md#阻塞处理) 给出具体步骤和影响并明确申请。当前功能完成后，推进下一个具备条件且获授权的功能。

现有接口可提前只读核查以发现可行性问题，但不以接口现状替代需求定义，不在需求未确认时提交接口设计审查或生成实施任务清单。按当前明确范围依次推进，不要求先确认整个系统；有效的历史需求、接口确认和实施授权继续沿用，从最早未完成阶段接续。

## 必要约束

- 当前范围由本次用户请求、适用资料及有效确认确定。相邻功能、示例或另一运行的内容不自动纳入；上下文不完整时只列已知范围与缺口。
- 主控统一记录授权，各任务引用同一有效方案，并按 [授权交接](references/coordination.md#授权交接) 明确传递已批准范围、依据和边界。接收方沿用有效授权，范围内开发、修复和复验持续推进，不因换角色、子代理或会话重复请求确认。
- 同一交付目标的可预见操作按 [完整操作清单与合并授权](references/coordination.md#完整操作清单与合并授权) 集中核查和申请；获批后连续执行，不逐项反复确认。新增范围、实质风险变化及用户明确要求的确认点仍单独处理。
- 保留已有改动；默认将任务分支合回已核实的开发基线分支，合并方式沿用仓库约定，记录在实施清单中，不单独询问常规 Git 选项。已有提交合并授权且审核测试条件满足后自动执行；仅在存在歧义或影响其他工作时询问相关决策。未获提交合并授权的随实施清单集中申请，不扩大到未授权工程、数据操作、远程推送和外部副作用。
- 各目标仓库分别加载并落实自身适用规范，主控与子代理均遵循 [协调规则](references/coordination.md) 的规范加载要求；交付前按 [验收规则](references/acceptance.md) 核查实际变更，编译和业务测试不能代替规范检查。
- 独立子代理只在当前工具和授权允许时使用；不可用时串行执行。角色范围是任务约束，不是文件系统沙箱。
- 各端按实际参与记录；工程检查、Mock、真实联调、功能和视觉分别报告。角色自报完成需主控核对。
- 主会话停止后不承诺自动唤醒或永久后台运行；以有效记录和实际状态恢复。

## 与 Superpowers 配合

按当前可用技能选择：需求与设计使用 brainstorming；当前范围的需求、接口及逻辑已确认后，使用 writing-plans 制定实施计划；获实施授权后，开发选择适用的 executing-plans 或任务级开发方法。业务测试、调试、审核和完成判断分别使用对应 Superpowers 能力。只加载当前阶段所需内容；已完成且有效的确认不重做。

本 Skill 负责跨工程调度。不要将 Superpowers 的顺序实现流程原样解释为允许多个实现任务并行；并行必须满足协调参考中的条件。主控自身已按本 Skill 协调时，子任务不再递归组织整套功能工作流。

不加载或依赖 controlled-development。用户明确要求、适用项目规范与实际工具约束优先于技能默认习惯。缺少某项技能或工具时说明影响，继续独立且已授权的工作，不虚构能力。
