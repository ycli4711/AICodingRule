# 服务启动诊断与恢复细则

### 服务启动诊断与恢复

启动前核对项目约定的启动命令、工作目录、必要配置来源及当前工具权限。优先复用本任务同版本且健康的服务；需要启动时保留可追踪的进程或终端身份及日志位置。Windows 后台启动使用隐藏窗口，除非用户要求可见交互窗口。不把某种 sandbox/approval 组合或某个启动器写成项目启动的固定前提，不修改全局安全配置来恢复服务。

失败先按实际执行阶段定位，不将所有现象统称为“项目无法启动”：

| 阶段 | 必要证据与处理 |
| --- | --- |
| 命令未获执行 | 保留完整命令、工作目录、工具返回及已提供的审批理由，敏感参数脱敏；检查当前权限和正式申请能力。不能将工具拒绝当作应用启动日志或代码故障 |
| 进程启动后退出 | 检查退出码和启动日志，定位依赖、配置、构建或端口等实际错误；仅在已授权范围修复，不因出现启动错误就扩大业务修改 |
| 进程运行但服务不健康 | 核实进程归属、实际监听地址、健康接口及页面真实请求，排查就绪状态和连接配置；有进程或返回页面 200 均不能单独证明业务链路可用 |

**业务授权与工具权限分别核对。** 已授权的启动操作如需额外权限，且当前宿主允许申请，使用其正式审批或权限申请机制，提交具体命令、工作目录、必要路径/网络范围、用途及实际影响，申请最小必要权限；不重新索取已有业务授权，也不将业务授权等同于工具已放行。当前策略不允许申请时，不发送不支持的提权参数，明确缺少的能力和可行的解除条件。

**正式审批不是绕过拒绝。** 实际审批拒绝后，按返回理由检查是否存在合规的更安全方案，或可补充证明授权与风险的证据；仅在宿主规则允许且有新依据时通过正式机制重新申请，不盲目重试。不得为规避拒绝换 shell、改写脚本、包装同一操作或切换到另一个执行工具。无法安全继续时，单独说明被拒绝的动作、审批返回的理由及仍需用户处理的事项；其他独立已授权工作继续。

仅有通用拒绝信息时标明“具体命中规则未知”，不猜测为 `never`、`Start-Process`、自动审批或 Windows 拦截导致。当前权限状态不能倒推历史状态；重新执行成功只证明本次条件下成功，不证明旧拒绝的具体原因。不要求用户提供凭据，也不为追因收集无关日志或敏感配置。

恢复后核验本任务进程归属、服务健康及受影响页面的真实请求，记录有效启动方式、配置来源、实际地址和验证范围，然后继续原任务。旧拒绝原因未明但已不影响当前工作时，保留该缺口，不将历史追因继续列为启动阻塞；用户明确要求追因时单独查证，不混淆“服务已恢复”和“旧拒绝原因已查明”。
