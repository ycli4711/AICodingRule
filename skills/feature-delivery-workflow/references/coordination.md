# 项目绑定、任务协调与恢复

## 绑定真实工作对象

从用户明确路径、当前工作区、有效运行记录或宿主的已保存项目列表获取路径。宿主能力以当前工具为准；截图名称用于匹配，不能推导磁盘路径。没有可核实来源时请用户提供路径，不全盘猜测搜索。

核对路径存在、工程身份及适用规范，向用户展示“端 → 工程 → 绝对路径 → 来源/核查状态”。名称重复、路径冲突或项目身份不明先澄清。明确绑定可纳入功能方案一次确认；绑定本身不是写入授权。

各任务运行命令明确指定自己的工作目录。同一仓库可承载多个端；公共模块单独说明归属。另一个工程的 MCP 配置不会因为记录了路径就自动进入当前会话，须核查真实工具可用性。

实施前记录各仓库 HEAD/分支、已有未提交内容及相关文件基线；非 Git 工程记录适当文件基线。检查已知并发任务，保留已有工作。工作树是否适合由具体工程决定，不能假设新工作树包含现有未提交依赖，也不自动提交或移动用户改动。

## 分支与运行环境

需求与设计阶段在现有工程只读核查。实施计划记录每个 Git 仓库的开发基线分支及提交、任务分支/worktree、必要审核测试条件，以及自动提交合并的授权。开发基线是本任务实际开始开发所依据的分支，依据有效运行记录和 Git 状态核实，不能仅用执行时恰好检出的分支代替；任务完成默认合回该基线分支，不默认合到 main。

合并方式沿用仓库规范或明确的既有流程。无规定且无实质歧义时由执行者选择保留已有提交历史的常规方式，能快进则快进，否则普通 merge，不为选择 squash 或 merge commit 单独询问用户。默认目标和方式写入实施清单即可；已有提交合并授权继续有效。仅在基线无法确定、约定冲突、用户另有目标，或操作会影响其他工作时集中说明具体分歧并询问，不能把可自行核实的 Git 选项交回用户。尚未取得提交合并授权的，与服务、数据和浏览器验证操作一并申请，不重复索取已有授权；远程推送仍单独明确是否包含。

实施确认后、开始写代码前，为相关仓库创建独立任务分支和 worktree，或复用本任务已有且符合条件的 worktree；使用实际起点，不依赖工具默认分支。执行者均在分配的目录工作，记录分支、路径和基线。非 Git 工程或工具确实不支持时说明限制，采用已确认的替代方式，不伪称已隔离。

新 worktree 不包含原目录未提交内容。开始前核对已有改动的归属和依赖；需要带入时保留原目录，用可核对的补丁或文件副本转入本任务必需内容并验证一致性，不能清空、重置、自动 stash 或移动用户改动。无关改动不纳入任务提交；归属不明且影响提交时集中澄清。进行中任务采用新规则时先核实当前状态，不为套流程重做开发、盲目迁移或覆盖已有成果。

联调从任务 worktree 启动，前端、后端及必要代理使用无冲突的独立端口，并核对浏览器、代理和 API 实际指向本分支服务。复用已确认的共享开发数据库和 Redis，不强制另建数据环境或隔离消息消费者；共享数据写入、迁移及后台副作用按完整操作清单的有效授权执行。独立分支和端口不代表数据隔离，不默认获得生产环境操作或删除现有数据权限。

审核测试达到预先确认的合并条件后，主控核对实际差异、证据版本及当前目标分支，自动仅提交本任务内容并按约定方式合并，不再次请求逐步批准。目标分支变化时先核对新增差异及必要集成验证；合并冲突、目标工作区有会被覆盖的改动、必需检查失败或证据不足时暂停合并并说明具体缺口，不强制覆盖、不降低通过条件。多仓库分别核验并报告结果，部分成功不宣称全部完成。

合并后核对目标提交与必要集成结果，记录提交和合并结果；不机械重跑未受影响的全部检查。随后按下节自动清理本任务临时资源，保留用户及其他任务资源。自动提交合并不等于自动部署或远程推送。

### 合并后的自动清理

本流程的收尾包含安全移除本任务创建的 worktree 和临时分支，不再次逐项申请。清理前逐仓库核实：任务成果已完整进入预定目标分支；任务 worktree 无已暂存、未暂存或未跟踪内容，忽略文件中无需要保留的成果；没有服务、构建进程或其他任务仍占用该目录，临时分支没有被其他 worktree 使用。普通合并可用提交包含关系核验；压缩合并等不能仅凭祖先关系判断，须另核对实际成果。无法证明已合并或存在待保留内容时保留资源并说明具体缺口。

核实本任务服务身份及无后续依赖后，按已有授权停止占用进程；不停止用户或其他任务进程。记录任务分支、提交和合并结果，将必要证据保存在目标仓库或其他保留位置，不能只存于待删除目录。核对 worktree 的绝对路径确为本任务创建的目录，不能删除原始工作区或目标分支所在目录。

先使用宿主管理的 worktree 归档/清理能力（若由宿主管理），否则使用 Git 的安全 worktree 移除命令，再安全删除本任务临时分支。禁止强制移除、强制删分支、硬重置或递归删除目录来绕过保护；安全命令拒绝时核查原因并报告，不能自动改用强制选项。保留目标分支、其他分支和其他任务改动，不扩展删除远程分支。最后核验 worktree 与分支列表，报告已清理或保留原因；用户明确要求保留的资源不清理。

## 各仓库规范加载与落实

进入任一目标仓库实施前，分别读取该仓库适用的上级、根目录及目标路径下的 `AGENTS.md`，以及它们引用的、与任务相关的语言和工程规范。不假定主会话已自动加载其他仓库的规则，也不把前端规则套到后端。引用文件缺失时核查现有目录或替代来源，记录真实缺口；影响实现选择时澄清，只暂停受影响部分，不能声称已读取不存在的规范。

只提取本次变更适用的强制约束及来源，例如分层与继承、依赖注入、类型与契约、注释与格式、SQL 位置和检查命令；在现有任务记录中简短关联，不另造整套规范文档。具体语言、框架和基类规则留在所属项目，不复制进通用 Skill。参考代码须先对照明确规范，历史写法或既有违规不能自动成为例外；规则冲突按适用层级及用户有效指令处理，仍不明确时说明冲突和影响，不自行放宽要求。

任务简报提供目标工作目录、规范的具体路径及相关约束。子代理在写入前自行读取其任务范围的适用规范，不能只依赖主控摘要或“遵守项目规范”一句话；完成时报告实际变更的规范核查结果、依据及缺口。跨目录新增文件时补读新路径适用规则，主控按验收规则复核，不能仅接受执行者自报合规。

## 分派条件与任务简报

默认一个活动功能，不等于一个执行者。主控先判断哪些能力需实现、哪些可复用；前后端存在可独立推进的工作且工具、授权允许时，优先分派内部子代理并行实施，主控也可承担其中一项。角色数按实际工作确定，不为凑角色拆分小任务。

并行前检查：实施授权有效、交互和契约一致、各任务所需依赖满足、修改范围不重叠、共享资源有唯一负责人。不同仓库不必然独立；实际共享的类型定义或配置由唯一负责人修改，依赖该变化的部分等待交接，不因文件类型相同就将无关任务串行化。

### 分开判断开发与联调依赖

- **开发依赖**：实现当前部分所必需的已确认需求、契约、共享定义及项目核查条件。条件已满足的后端实现与前端工作可同时启动，不默认等待后端全部完成。
- **联调依赖**：接口在约定环境可调用、实际 Schema 核验及必要测试条件。环境尚未就绪只阻塞依赖它的对接或真实联调，不自动阻塞其他开发。
- **项目约束优先**：项目要求先经 MCP 核对 Schema 时，正式 API 字段及请求对接遵守该前置条件；单独判断布局、列渲染和交互等工作是否不依赖新 Schema、且允许先行。约束确实覆盖整个前端开发时遵循该约束，不借拆任务绕过。测试样例不能冒充真实接口或联调证据。

实施计划简短列明各端执行者、可并行部分、必须等待的部分及解除条件。选择串行时给出具体依据，例如共享文件冲突、契约未定、工具不可用或任务过小，不只写“主控串行”。只有部署或数据库环境阻塞时，继续独立可完成项，不据此扩大环境操作授权。依赖解除后及时交接；工具允许时实际启动任务，不能仅把计划中的分工写成“并行中”。

给执行者的最小上下文应包含：

- 当前运行及功能标识、目标、范围来源、明确排除项。
- 本任务工作目录、可修改范围、适用用户与项目规范。
- 当前角色 Skill 的实际路径、该角色需要读取的规范来源及预期交付；按主控阶段路由选择，不要求执行者同时承担所有角色。
- 已确认需求（含交互）、接口及逻辑的版本，随后制定的实施计划、实施授权依据和已有改动基线。
- 输入和依赖、可先行部分、完成条件、验证与操作边界。
- 共享文件或设备负责人、报告去向及产物路径。

不要只传“按上文做”。执行者看不到完整上下文时，主控补齐必要事实；不允许它从同名历史任务、另一案例或惯常页面功能推测本次范围。

子代理职责是在简报范围实施或验证，不再递归开启整套工作流。主控负责确认、全局状态和最终交付。角色报告写各自记录，公共方案与进度由主控串行更新。

### 授权交接

向子代理分派任务或经用户授权通知其他会话时，主控必须明确传递本任务有效授权，不能只说“按最新 Skill 执行”或“授权不明时再申请”。交接简短写清：用户确认的原意或可核实记录、适用任务与仓库/环境、已批准操作及完成条件、仍需确认的具体操作和明确排除项；注明哪些可直接继续，不能用笼统保留条款把已批准事项重新变成待确认。

区分“修改通用 Skill”与“批准该流程用于当前任务”：前者本身不授权业务操作；用户已明确同意当前任务执行的，按其实际范围传递，不能降格为仅更新文档。原话、有效上下文和记录共同作为依据，不伪造或扩大授权。授权范围内的端口、路径等常规实施细节由执行者核实处理，不重新包装成整项实施申请。

接收方核实交接来源及适用范围后直接沿用已有授权，不要求用户因切换执行者再确认。缺上下文时先查记录或请主控补充依据，不直接将同一问题退回用户；仍有实质歧义、冲突、新增范围或风险变化时，只针对缺口集中询问。用户的后续撤回、暂停或范围调整优先；主控及时同步相关执行者，更新旧的待确认状态，避免继续等待已解决的问题。

授权交接不自行授予向其他会话发消息的权限，也不改变工具权限限制。发现此前传递有误时，在已有通信授权内明确更正具体范围并通知接收方，不只在原会话解释原因。

## 执行效率

- **清洁构建前检查占用**：确需清理构建产物时，先核查本任务运行服务、构建进程及其输出目录，避免清理正在被加载或写入的产物。按进程身份、命令行和路径确认归属后，在已有授权内停止本任务相关进程并核实退出，再执行清洁构建；不按进程名称批量结束用户或其他任务进程。归属不明或服务仍被依赖时先协调，只暂停受影响构建。已有有效构建证据且无变化时，不为收尾新增清洁构建。

- **提前核查关键环境**：开始开发时用最小检查确认构建输出是否有并发写入、接口 Schema 的可用来源及测试前提，不默认启动全量构建。确有产物冲突时采用项目允许的隔离方式；同一任务复用隔离目录和可靠缓存，仅同步必要变化并核对源码版本，不反复复制整库或冷构建。不擅自修改 IDE、构建配置或终止用户进程。
- **契约及时交接**：契约稳定、相关代码可编译且当前版本文档可读取后，按项目要求完成 MCP 等核查，即可交接允许开展的调用端接入，不等待无关测试完成。文档可核对与真实接口可联调分别标记；临时文档服务、替身依赖不证明真实业务可用。
- **共享验证安排**：主控在现有计划中统一记录必要检查、执行者、版本及结果；同一构建输出目录指定唯一构建负责人，其他角色复用经核实的证据，不各自重跑。独立目录可并行；源码或依赖变化使证据失效时，只补受影响检查，项目强制检查仍须完成。清洁构建用于项目要求或有证据的产物污染，不按角色交接重复执行。
- **集中审核与复核**：首轮集中反馈已发现的问题，紧急缺陷及时通知；修复复核聚焦实际修复及其影响，不因角色切换重新审核全部未变化内容。新证据指向其他路径时补查，不为限时而漏掉相关缺陷。
- **减少无效协调**：交接消息围绕版本、就绪条件、缺陷和阻塞变化；等待构建优先使用完成通知或适当间隔的状态查询，避免频繁读取相同日志。耗时异常时区分仍在推进、失败和停滞，再决定处理，不将重复查询当进展，也不武断按固定时长中止有效工作。

## 通信与就绪

使用当前提供的任务创建、消息、追加任务、状态与等待工具。读取工具说明，不硬编码某个版本的参数。向已结束任务追加工作时使用能够触发其继续执行的能力；普通消息送达不代表任务已重新运行。没有协作工具时由主控串行承担职责，记录实际执行方式。

独立侧栏会话与内部子代理不同：只有用户明确要求时才创建或向这些会话发送消息，不能用内部协作授权替代独立会话通信授权。

| 角色报告 | 主控处理 |
| --- | --- |
| 缺上下文或条件 | 查资料，补上下文；重要口径缺失再集中问用户，只暂停依赖部分 |
| 建议改交互或契约 | 列变化与影响，核对授权，确认有效版本后通知所有受影响任务 |
| 接口或依赖就绪 | 检查环境、版本、具体就绪范围及调用/契约证据，再交接对应联调任务 |
| 缺陷 | 保留复现、预期、实际和证据，交负责角色修复及复验 |
| 本任务完成 | 核对实际差异和证据再更新状态，不等于整个功能验收完成 |

编译通过只能证明相应工程检查，不能直接升级为接口可联调。接口在约定环境可调用且符合当前契约、有必要验证证据后，才标“就绪”。一次只让其覆盖的调用端路径进入真实联调，不等待同功能其他接口全部完成，也不把它们一起标为就绪。

消息说明发生什么、影响哪个功能/版本、要谁做什么，并引用完整资料。共享文件保存事实，工具通知负责交接；必要时核对收到的任务结果。消息、报告和截图不包含凭据。

## 阻塞处理

遇到接口、环境、权限或工具阻塞，先核实原因，只暂停受影响部分，继续已有授权内可独立完成的工作。不能仅以“等待环境就绪”结束，也不能为了推进而绕过项目要求或扩大授权。

1. **核实阻塞**：说明缺少的具体条件、证据及受影响任务。区分代码未完成、文档未更新、环境版本不符、工具访问失败与缺少操作授权；某次接口搜索无结果不能直接证明必须部署或迁移数据库。
2. **准备解除步骤**：优先从现有配置、文档和只读工具核实目标环境、当前版本/结构、更新机制与执行者，形成最小必要操作及成功判据。能在已有授权内解决的直接推进；信息不足时只问无法自行核实且影响下一步的必要信息，不猜环境或命令。
3. **具体请求新增授权**：确需部署、数据库执行等未授权操作时，先完成独立可做的核查和准备，再一次性列出目标环境、完整操作范围、文件/数据对象、具体命令或脚本、影响、验证及必要回退方式，并说明为何超出原授权。资料过长可链接完整可审查文件并保留摘要，不只问“是否继续”，不重复申请已有授权。
4. **合并授权后连续执行**：同一目标中可预见的剩余操作，先按下节整理完整清单，再集中申请新增授权；获批后按依赖顺序连续执行、修复和复验，不逐项反复确认。
5. **保留恢复点并接续**：记录谁负责下一步、待补信息或待授权事项、解除条件和恢复任务。用户补充条件或授权后，先复核状态，再继续未完成部分；核验接口或环境真正就绪后才恢复对应联调，不重做已有效完成项，也不承诺自动后台唤醒。

不能只列遗留项就结束，也不能把“需要授权”仅作为备注。已授权且可执行的剩余必要工作继续做；需要新增授权的，完成上述准备后在当前回复中明确提出具体授权申请。目标环境或命令仍缺必要信息时，先明确询问缺失信息，不编造执行方案。详细步骤可链接可审查文件，但当前回复必须保留执行对象、操作范围、主要影响和待用户决定的内容。

对用户简短报告“卡在哪里、已核实什么、下一步由谁做什么、是否需要授权”；详细证据和操作清单放关联记录。确实无法继续时明确阻塞，不把局部实现或准备工作当作整个功能交付。

### 完整操作清单与合并授权

按当前交付目标核查可预见的依赖链，在已有实施计划中整理一份清单，不只准备眼前第一步。区分已完成、已授权可执行和确需新增授权的操作；已授权工作直接推进，不为等待清单而暂停独立工作，也不重新申请已执行成功的操作。

涉及本机联调时，按实际需要覆盖：服务启动/重启及受影响进程、端口和运行配置，接口与浏览器验证，测试数据准备及业务副作用，范围内修复复测，以及测试数据清理和服务恢复。写明目标环境、具体对象与命令或脚本、执行顺序、影响、成功判据及必要回退；不涉及的操作省略。浏览器只读检查与会写入数据、发送消息的提交操作分别说明；清理仅限本次明确创建且获准清理的数据，服务操作不能默认扩展到用户或其他任务进程。

将确需新增授权的部分合并成一次可审查申请，允许用户批准全部或明确子集；完整清单尚缺实质信息时，集中询问无法自行核实的缺口，不以模糊的“一次性全权授权”代替具体范围。用户明确要求某项单独确认时保留该要求。获批后，清单覆盖的启动、重启、测试、修复复测及清理按条件连续执行，不因换角色、换工具或进入下一步再次询问。只读浏览器验证等已有授权事项无需逐项确认。

仅在新增目标/环境/对象、超出批准范围的写入或副作用、实质风险变化，或用户明确要求的确认点出现时重新申请；只暂停受影响操作并继续独立已授权工作。正常范围内的技术调整不自动产生新审批；失败后先核实状态再决定是否安全重试，不以批量授权为由反复执行结果未知的写操作。

## 恢复与持续推进

恢复先读取运行记录，再核对实际状态：

1. 当前功能、有效范围与用户确认；后续消息是否改变口径。
2. 项目绑定、契约及相关代码版本，用户新增改动。
3. 旧证据是否仍覆盖当前版本，只将受变化影响的路径标待复验。
4. 工具返回的真实任务状态；记录中的旧 ID 不能证明代理仍存活。
5. 剩余最小任务、执行者和下一步。

可追加的存量任务继续使用；不可恢复时，在允许的条件下创建新任务或由主控串行处理。不要反复联系失效 ID，不重做证据仍有效的工作，不凭历史“已完成”跳过变化。

同类故障反复无进展时重新核对根因和任务划分。重要范围或副作用变化由用户决定；请求结果未知的写操作先核实是否已生效，不盲目重试。
