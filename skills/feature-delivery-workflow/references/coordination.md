# 项目绑定、任务协调与恢复

## 绑定真实工作对象

从用户明确路径、当前工作区、有效运行记录或宿主的已保存项目列表获取路径。宿主能力以当前工具为准；截图名称用于匹配，不能推导磁盘路径。没有可核实来源时请用户提供路径，不全盘猜测搜索。

核对路径存在、工程身份及适用规范，向用户展示“端 → 工程 → 绝对路径 → 来源/核查状态”。名称重复、路径冲突或项目身份不明先澄清。明确绑定可纳入功能方案一次确认；绑定本身不是写入授权。

各任务运行命令明确指定自己的工作目录。同一仓库可承载多个端；公共模块单独说明归属。另一个工程的 MCP 配置不会因为记录了路径就自动进入当前会话，须核查真实工具可用性。

实施前记录各仓库 HEAD/分支、已有未提交内容及相关文件基线；非 Git 工程记录适当文件基线。检查已知并发任务，保留已有工作。工作树是否适合由具体工程决定，不能假设新工作树包含现有未提交依赖，也不自动提交或移动用户改动。

## 各仓库规范加载与落实

进入任一目标仓库实施前，分别读取该仓库适用的上级、根目录及目标路径下的 `AGENTS.md`，以及它们引用的、与任务相关的语言和工程规范。不假定主会话已自动加载其他仓库的规则，也不把前端规则套到后端。引用文件缺失时核查现有目录或替代来源，记录真实缺口；影响实现选择时澄清，只暂停受影响部分，不能声称已读取不存在的规范。

只提取本次变更适用的强制约束及来源，例如分层与继承、依赖注入、类型与契约、注释与格式、SQL 位置和检查命令；在现有任务记录中简短关联，不另造整套规范文档。具体语言、框架和基类规则留在所属项目，不复制进通用 Skill。参考代码须先对照明确规范，历史写法或既有违规不能自动成为例外；规则冲突按适用层级及用户有效指令处理，仍不明确时说明冲突和影响，不自行放宽要求。

任务简报提供目标工作目录、规范的具体路径及相关约束。子代理在写入前自行读取其任务范围的适用规范，不能只依赖主控摘要或“遵守项目规范”一句话；完成时报告实际变更的规范核查结果、依据及缺口。跨目录新增文件时补读新路径适用规则，主控按验收规则复核，不能仅接受执行者自报合规。

## 分派条件与任务简报

默认一个活动功能，不等于一个执行者。主控先判断哪些能力需实现、哪些可复用；前后端存在可独立推进的工作且工具、授权允许时，优先分派内部子代理并行实施，主控也可承担其中一项。角色数按实际工作确定，不为凑角色拆分小任务。

并行前检查：实施授权有效、交互和契约一致、各任务所需依赖满足、修改范围不重叠、共享资源有唯一负责人。不同仓库不必然独立；实际共享的类型定义或配置由唯一负责人修改，依赖该变化的部分等待交接，不因文件类型相同就将无关任务串行化。

### 分开判断开发与联调依赖

- **开发依赖**：实现当前部分所必需的已确认需求、契约、共享定义及项目核查条件。条件已满足的后端实现与前端工作可同时启动，不默认等待后端全部完成。
- **联调依赖**：接口在约定环境可调用、实际 Schema 核验及必要测试条件。环境尚未就绪只阻塞依赖它的对接或真实联调，不自动阻塞其他开发。
- **项目约束优先**：项目要求先经 MCP 核对 Schema 时，正式 API 字段及请求对接遵守该前置条件；单独判断布局、列渲染和交互等工作是否不依赖新 Schema、且允许先行。约束确实覆盖整个前端开发时遵循该约束，不借拆任务绕过。测试样例不能冒充真实接口或联调证据。

实施计划简短列明各端执行者、可并行部分、必须等待的部分及解除条件。选择串行时给出具体依据，例如共享文件冲突、契约未定、工具不可用或任务过小，不只写“主控串行”。只有部署或数据库环境阻塞时，继续独立可完成项，不据此扩大环境操作授权。依赖解除后及时交接；工具允许时实际启动任务，不能仅把计划中的分工写成“并行中”。

给执行者的最小上下文应包含：

- 当前运行及功能标识、目标、范围来源、明确排除项。
- 本任务工作目录、可修改范围、适用用户与项目规范。
- 已确认需求（含交互）、接口及逻辑的版本，随后制定的实施计划、实施授权依据和已有改动基线。
- 输入和依赖、可先行部分、完成条件、验证与操作边界。
- 共享文件或设备负责人、报告去向及产物路径。

不要只传“按上文做”。执行者看不到完整上下文时，主控补齐必要事实；不允许它从同名历史任务、另一案例或惯常页面功能推测本次范围。

子代理职责是在简报范围实施或验证，不再递归开启整套工作流。主控负责确认、全局状态和最终交付。角色报告写各自记录，公共方案与进度由主控串行更新。

## 通信与就绪

使用当前提供的任务创建、消息、追加任务、状态与等待工具。读取工具说明，不硬编码某个版本的参数。向已结束任务追加工作时使用能够触发其继续执行的能力；普通消息送达不代表任务已重新运行。没有协作工具时由主控串行承担职责，记录实际执行方式。

独立侧栏会话与内部子代理不同：只有用户明确要求时才创建或向这些会话发送消息，不能用内部协作授权替代独立会话通信授权。

| 角色报告 | 主控处理 |
| --- | --- |
| 缺上下文或条件 | 查资料，补上下文；重要口径缺失再集中问用户，只暂停依赖部分 |
| 建议改交互或契约 | 列变化与影响，核对授权，确认有效版本后通知所有受影响任务 |
| 接口或依赖就绪 | 检查环境、版本、具体就绪范围及调用/契约证据，再交接对应联调任务 |
| 缺陷 | 保留复现、预期、实际和证据，交负责角色修复及复验 |
| 本任务完成 | 核对实际差异和证据再更新状态，不等于整个功能验收完成 |

编译通过只能证明相应工程检查，不能直接升级为接口可联调。接口在约定环境可调用且符合当前契约、有必要验证证据后，才标“就绪”。一次只让其覆盖的调用端路径进入真实联调，不等待同功能其他接口全部完成，也不把它们一起标为就绪。

消息说明发生什么、影响哪个功能/版本、要谁做什么，并引用完整资料。共享文件保存事实，工具通知负责交接；必要时核对收到的任务结果。消息、报告和截图不包含凭据。

## 阻塞处理

遇到接口、环境、权限或工具阻塞，先核实原因，只暂停受影响部分，继续已有授权内可独立完成的工作。不能仅以“等待环境就绪”结束，也不能为了推进而绕过项目要求或扩大授权。

1. **核实阻塞**：说明缺少的具体条件、证据及受影响任务。区分代码未完成、文档未更新、环境版本不符、工具访问失败与缺少操作授权；某次接口搜索无结果不能直接证明必须部署或迁移数据库。
2. **准备解除步骤**：优先从现有配置、文档和只读工具核实目标环境、当前版本/结构、更新机制与执行者，形成最小必要操作及成功判据。能在已有授权内解决的直接推进；信息不足时只问无法自行核实且影响下一步的必要信息，不猜环境或命令。
3. **具体请求新增授权**：确需部署、数据库执行等未授权操作时，先完成独立可做的核查和准备，再一次性列出目标环境、完整操作范围、文件/数据对象、具体命令或脚本、影响、验证及必要回退方式，并说明为何超出原授权。资料过长可链接完整可审查文件并保留摘要，不只问“是否继续”，不重复申请已有授权。
4. **保留恢复点并接续**：记录谁负责下一步、待补信息或待授权事项、解除条件和恢复任务。用户补充条件或授权后，先复核状态，再继续未完成部分；核验接口或环境真正就绪后才恢复对应联调，不重做已有效完成项，也不承诺自动后台唤醒。

对用户简短报告“卡在哪里、已核实什么、下一步由谁做什么、是否需要授权”；详细证据和操作清单放关联记录。确实无法继续时明确阻塞，不把局部实现或准备工作当作整个功能交付。

## 恢复与持续推进

恢复先读取运行记录，再核对实际状态：

1. 当前功能、有效范围与用户确认；后续消息是否改变口径。
2. 项目绑定、契约及相关代码版本，用户新增改动。
3. 旧证据是否仍覆盖当前版本，只将受变化影响的路径标待复验。
4. 工具返回的真实任务状态；记录中的旧 ID 不能证明代理仍存活。
5. 剩余最小任务、执行者和下一步。

可追加的存量任务继续使用；不可恢复时，在允许的条件下创建新任务或由主控串行处理。不要反复联系失效 ID，不重做证据仍有效的工作，不凭历史“已完成”跳过变化。

同类故障反复无进展时重新核对根因和任务划分。重要范围或副作用变化由用户决定；请求结果未知的写操作先核实是否已生效，不盲目重试。
