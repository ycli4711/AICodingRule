# 验证与收尾

授权遵循 [方案与授权](feature-design.md#唯一授权规则)，资源协作遵循 [执行协作](coordination.md)。本文件统一规定证据、完成条件和清理，不新增审批。

## 一份验证安排

在统一方案中按变更风险及项目强制要求选择检查，记录范围、负责人、版本/环境与结果。文档、注释等无运行行为或契约变化的修改只做局部检查；样式按影响做视觉检查，不机械新增业务测试、全量构建或 TDD。

开发者自查并完成必要自测；审核者检查实际差异和项目规范；测试执行者复用有效自测证据，补行为、真实联调与适用视觉缺口。不同结论不能相互冒充，但不要求相同命令由不同角色各执行一次。主控核对版本、范围、证据缺口和完成条件，不再完整重做角色审核；有矛盾或缺口才定向核验。

覆盖受影响的成功、失败、关键边界及必要/禁止的副作用。共用逻辑取代表入口，独立逻辑或副作用分别检查；权限、重试、幂等、并发、性能等仅在实际相关或项目要求时纳入。静态解析、Mock 和构建不证明真实接口或数据库行为；异步接受与最终效果分开验证。性能结论需测量依据。数据库验证注明当前模式、实际目标及 SQL 执行/核验结果；沙盒通过不等于真实开发库已迁移或真实联调通过，未执行环境和部署前迁移事项须明确列出。

验证工具按目标平台及实际能力选择，使用专用工具前读取相关规则；工具缺失不伪称已验。视觉对照保持参考、视口、状态和数据可比，功能正常不替代视觉符合。

依据原型交付时，按 [原型偏离关口](feature-design.md#原型偏离关口) 核对实际实现与参考、已批准差异清单：分别验证字段含义与操作行为、表格结构与信息层级及关键布局。无横向溢出、接口成功或构建通过均不能代替原型一致性验证。报告已批准差异、未批准偏离及未验证范围；未批准偏离仍存在时，不得宣称原型一致性验收通过，须交回对应关口处理，不在验证阶段自行接受或修订设计。

## 页面与子视图实际视觉验收

涉及页面展示或交互时，开发自测须在实际浏览器中打开待验收版本并检查最终渲染。逻辑测试、Mock、接口成功、DOM 中存在文本或构建通过，均不能代替页面检查；本节不替代用户人工验收。

- **逐页实现、及时对照**：每个页面的主要视图形成可运行结果后，即按该页原型基线，在可比视口、状态和内容下检查布局、字段、操作及关键子视图，记录差异和复验结果，不等全部页面完成才统一检查。拟推广到相似页面的布局或组件模式先核对代表页面，发现偏差先修正再推广；后续页面仍核对自身差异。多个独立页面可并行推进，公共逻辑无需重复验证。环境或样本不足时标明未验证范围，继续独立工作，不将未经核对的页面模式当作已通过样板。
- **不新增逐页审批**：逐页对照属于已授权实施中的自测，符合基线时直接继续；范围内实现偏差直接修复。只有新增实质设计偏离或授权范围变化才按原有规则申请对应增量确认，最终人工验收关口保持不变。
- **按视图覆盖**：依据方案列出受影响的页面及列表、编辑弹窗、详情抽屉、审批弹框等子视图，逐项记录已检查、未检查或不适用。共用逻辑可复用测试证据，但不同容器、入口和布局须核对实际显示；不能检查一个入口就推定其他入口正常。
- **使用代表性内容**：按影响覆盖非空与空状态、长正文、多条明细或历史记录；有相关风险时补加载失败、切换记录等状态。优先复用已授权样本；沙盒合成样本只支持对应展示结论，不冒充真实业务流程证据，不为补样本修改用户数据或擅自提交审批。
- **检查完整可见区域**：实际打开、展开并滚动到相关内容与底部操作区，必要时横向滚动。核对数据行、字段和值、换行与长内容、重复信息、遮挡、裁切、容器高度及按钮可见可操作。以已确认原型和项目约定判断，不将个人风格偏好当缺陷，也不擅自改变设计。
- **数据对应可见结果**：选同一记录核对来源或接口与实际屏幕。例如接口返回两条审批节点，应实际看到对应人员、时间和意见；有表头、接口有值或 DOM 有文本但内容区不可见，仍判展示失败。无法解释的空白不能当正常空态通过。
- **逐页保留对照证据**：在同一记录按“页面/子视图｜原型参考｜实现截图｜差异及结论”简记；共同版本、环境、视口及样本状态集中说明。截图须来自待验收版本并经过实际查看，覆盖本次关键区域；交互结论另附实际操作及可见结果。无原型时如实注明并使用已确认设计依据，不虚构参考。已有有效证据直接链接，不另建重复报告，只补受变更或缺口影响的部分。

交付前按方案页面清单核对上述证据，逐项标明通过、失败或未验证；不适用须说明原因。缺少参考查看或实际页面对照证据、仍有未批准偏离的视图，不得标为视觉通过，也不能将局部通过概括为整项工程自检完成。主控核对证据覆盖与结论，不要求重复执行有效检查；此项属于内部自测，不新增逐页用户审批。

修复后回到原失败视图及同根因影响的容器复验。缺少浏览器、样本、权限或环境时明确具体未验证范围，继续独立工作，不把页面视觉验收标为通过。交付分别说明“逻辑测试／真实流程／视觉检查”的范围与结果；测试项数不代表页面覆盖，局部通过不能概括整个页面或功能完成。

## 证据有效性与增量检查

复用前核对证据覆盖的行为、代码状态（提交与未提交差异）、契约、相关依赖/配置、运行环境及数据前提。相关条件变化、失败、新风险或覆盖缺口使对应证据失效；无关文件变化、角色切换、阶段切换和会话续接不自动使其失效。无法判断影响时做定向核查，不能直接认定有效。

只补失效或缺失部分，并检查实际副作用和相关入口；不重复未受影响的命令、全量构建或报告。项目强制检查仍须执行。人工验收适用版本及代码变化后的复验仍按下文验收规则处理，不能用工程证据替代用户验收。

## 展示数据核对

涉及页面数据展示或其数据链路变更时，将数据正确性纳入开发自测和真实联调；页面能打开、请求成功、占位文案正常显示或布局符合均不能替代此项。复用同版本有效证据，不新增逐字段审批或重复报告。

- **识别关键字段**：依据已确认业务、原型和接口契约，识别本次受影响的记录身份、关联对象、金额、状态及操作前提等关键字段；关键不等于必填，不自行将所有字段设为必填。
- **缺失必须追源**：关键字段显示“未提供”、`--`、空白或异常默认值时，核对同一记录的“来源数据／业务快照 → 实际接口响应 → 页面映射与可见结果”，定位首次缺失或失真的环节并查明原因。来源为空仍须核实其产生链路及当前阶段是否允许缺失；不能仅凭接口返回空值、字段可空或前后端一致判为正常。历史快照按对应契约判断，不直接用当前主数据替代；零值等有效值不能误判为空。证据不足时保留缺口，不推测原因或补造业务值。
- **核对操作影响**：明确缺失是否影响当前展示、关联识别及后续操作，按已确认业务检查应允许或阻止的行为。不能未经业务依据自行禁用按钮、增加必填校验或放宽操作条件；口径不明时集中澄清，不逐字段重复审批。
- **覆盖有效样本**：每类独立展示逻辑使用有代表性的非空数据，按实际风险补空值及不适用状态；不能只凭全空样例通过。按影响核对名称/关联、枚举、数量/单位、日期及明细，检查滚动、折叠、附件及切换记录后的残留值，不穷举无关组合。沙盒样本不完整时按已授权的数据准备规则补齐后再验，合成样本仅支持对应局部结论，不冒充真实链路证据。

按以下依据判定，不能把已知缺陷降格为样本不足或未验证：

| 情况 | 验收判定 |
| --- | --- |
| 已确认允许为空，当前记录满足条件，展示及操作符合规则 | 对应检查可通过，简记允许为空的依据；不能代替应有值场景验证 |
| 本应有值，但来源、接口或页面存在缺陷 | 不通过，记录缺陷环节及影响 |
| 缺失原因、业务口径或必要证据未查清 | 未验证，不得通过 |
| 沙盒或其他必要样本不完整，无法验证正常展示 | 对应范围未验证，补齐合法样本后再验 |

每项异常在同一记录简记一行：“字段｜样本标识｜应有值或允许为空的依据｜缺失环节及原因｜处理结果与证据”。尚未查清的内容明确标记未知及下一步；正常字段集中概述。范围内实现缺陷直接修复并复测原场景及同根因受影响入口；源数据问题按统一授权处理，不为验收通过修改用户数据或伪造业务事实。

关键字段缺失仍不通过或未验证时，明确受影响页面和操作范围，不能宣称该范围验收通过或整项工程自检完成；独立已验证部分可分别报告，不将局部通过概括为整体完成。

## 缺陷与证据

缺陷记录必要的前置条件、复现、预期依据、实际结果、影响与证据，区分实现、测试、环境和需求问题；同根因集中报告。已有修复授权持续有效。修复后复核实际变化，复测原失败场景及相关影响；仅新变化、失败或证据缺口扩大检查，不重跑未受影响的全部回归，不删除断言或放宽契约求通过。

按实际相关端和检查项记录通过、失败、未验证或不适用，附范围、版本、环境及依据；无需为每个维度另建报告。核实测试是否实际启用、失败/跳过情况，不能只看退出码；既有失败只查与当前结论的关联，无关问题记录后停止扩展。

## 验收环境恢复

联调环境中断、旧运行目录缺失或端口未监听时，按 [服务启动诊断与恢复](service-recovery.md#服务启动诊断与恢复) 核对可用运行时、项目启动配置和目标环境。沿用已记录的数据库模式。若模式尚未确定，先按 [数据库环境](database.md#数据库环境) 落实选择。使用现有工具在授权范围内尝试恢复服务或重建任务隔离环境，核验服务健康、应用实际连接目标及受影响页面的真实请求。独立且已授权的验证继续。

恢复后接续真实流程与页面视觉验收。仍无法继续时，分别说明两类验收已验证与未验证的范围，并记录失败步骤、已执行的命令和工作目录、实际错误、已尝试的恢复措施及恢复点。需要用户介入时，给出具体操作及完成后可继续的条件。

## 工程完成与人工验收

工程完成条件：确认范围已实现或有复用依据、契约一致、必要项目规范与工程检查通过、适用真实联调/功能/视觉验证完成、影响完成条件的问题关闭。由当前证据支持结论，不因用户未回复就撤销工程完成事实。

**正式业务开发默认必须经用户人工验收通过，才能合并或回写开发基线。** 仅用户明确免除人工验收时可跳过；未约定、未回复、批准实施、允许联调、完成登录或 SQL 执行、代理自测通过，都不构成验收通过或免除。记录用户原意、适用任务范围及待验收版本；泛泛的“继续”不能替代明确验收结论，有歧义时只澄清该关口。

**合并关口按实际效果判断**：Git merge、cherry-pick、文件复制、补丁应用、增量回写等，只要把任务成果整合到原开发目录或目标基线，都须先满足人工验收关口，不能因未产生 Git 提交而跳过。任务隔离目录内的开发、自测和已授权修复可继续，不因此阻断必要验证。

人工验收是正式业务开发的默认交付关口，无需询问用户是否增加；主控须将该条件及当前状态随任务简报传给执行者。开发、自测及必要审核完成后报告“工程自检完成，待人工验收”，保留验收浏览器标签页、前后端及必要依赖服务、worktree 和所需测试数据；不得因本轮回复结束就关闭、停止、删除或提前合并。提供可直接打开的地址、简短验收路径、样本及已知限制，确保展示的是待验收版本，明确真实数据与测试替身的区别。记录进程与端口等恢复信息，不承诺服务永不退出；环境中断时在已有授权内恢复，不让用户重新配置启动。

等待期间不重复审核测试，不把沉默当验收通过。用户反馈问题后在授权范围修复、针对性复测并保留环境供复验；用户明确通过，或明确免除人工验收且工程条件满足后，按已确认方案自动连续执行提交、合并或回写、远程推送、远程核验及清理，无需逐项再问。验收通过或免除均不覆盖原有“不提交/不推送”等限制，也不授权新的操作范围。验收后若实质改变已验收行为或契约，修复并验证后对受影响部分重新交付人工复验，除非用户明确免除的范围涵盖该变化；不把旧版本通过无限沿用到新变化。

仍有独立可执行工作继续做；只剩已核实外部条件或增量授权阻塞时，按协调规则给出明确请求和恢复点，报告部分完成，不将未验证记为通过。用户要求只交阶段成果时准确注明边界。

### 同步交付代码验收

**提交用户人工验收时，同一条交付消息须同时提供功能验收和代码验收材料**，不能只给页面地址、自测通过结论或文件名清单。详细内容复用同一主记录和已有审核证据，不另建重复报告。

- **可查看的实际差异**：标明仓库、任务目录/分支、比较基线及待验收版本，提供可直接打开的 diff/审核入口。无现成入口时提供完整差异文件或可直接执行的准确查看命令；覆盖本任务已提交、暂存、未暂存及未跟踪的新文件，排除无关改动。未提交内容说明其状态，不能只用 HEAD 代表待验收版本；不得为生成审核入口擅自提交、推送或创建 PR。
- **代码阅读指引**：按业务变化概述关键文件与实现入口、设计取舍和影响范围，给出可定位的文件链接或行号，帮助用户检查代码质量。重点按实际风险覆盖职责与分层、可读性、重复逻辑与复用、项目规范、异常及边界处理，以及相关安全、性能和可测试性；不要求所有任务填满固定检查表。
- **质量审核结论与证据**：区分开发者自查、独立审核和用户代码验收，说明实际审核范围、发现及修复情况、未解决问题、必要验证结果与未验证项。复用同版本有效证据；未发现问题不能表述为保证无缺陷，功能测试通过也不能替代代码质量结论。

功能验收与代码验收属于**同一个人工验收关口**，集中请求用户确认，不拆成两轮固定审批。完整展示两类材料后，用户明确整体“验收通过”可覆盖两者；用户只确认功能或只确认代码时，记录对应结果，另一项仍待验收，除非用户明确免除。已有明确覆盖两者的验收或免除继续有效，不重复索取。

验收期间发生代码变化时，同步更新实际差异、版本标识和受影响的审核结论，向用户说明复验范围；纯代码质量调整也不能沿用变更前的代码验收结论。未受影响的功能或审核证据继续复用，不因此重跑全量验证。
