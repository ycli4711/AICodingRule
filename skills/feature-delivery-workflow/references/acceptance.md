# 验证与收尾

授权遵循 [方案与授权](feature-design.md#唯一授权规则)，资源协作遵循 [执行协作](coordination.md)。本文件统一规定证据、完成条件和清理，不新增审批。

## 一份验证安排

在统一方案中按变更风险及项目强制要求选择检查，记录范围、负责人、版本/环境与结果。文档、注释等无运行行为或契约变化的修改只做局部检查；样式按影响做视觉检查，不机械新增业务测试、全量构建或 TDD。

开发者自查并完成必要自测；审核者检查实际差异和项目规范；测试执行者复用有效自测证据，补行为、真实联调与适用视觉缺口。不同结论不能相互冒充，但不要求相同命令由不同角色各执行一次。主控核对版本、范围、证据缺口和完成条件，不再完整重做角色审核；有矛盾或缺口才定向核验。

覆盖受影响的成功、失败、关键边界及必要/禁止的副作用。共用逻辑取代表入口，独立逻辑或副作用分别检查；权限、重试、幂等、并发、性能等仅在实际相关或项目要求时纳入。静态解析、Mock 和构建不证明真实接口或数据库行为；异步接受与最终效果分开验证。性能结论需测量依据。

验证工具按目标平台及实际能力选择，使用专用工具前读取相关规则；工具缺失不伪称已验。视觉对照保持参考、视口、状态和数据可比，功能正常不替代视觉符合。

依据原型交付时，按 [原型偏离关口](feature-design.md#原型偏离关口) 核对实际实现与参考、已批准差异清单：分别验证字段含义与操作行为、表格结构与信息层级及关键布局。无横向溢出、接口成功或构建通过均不能代替原型一致性验证。报告已批准差异、未批准偏离及未验证范围；未批准偏离仍存在时，不得宣称原型一致性验收通过，须交回对应关口处理，不在验证阶段自行接受或修订设计。

## 展示数据核对

涉及页面数据展示或其数据链路变更时，将数据正确性纳入开发自测和真实联调；页面能打开、请求成功或布局符合不能替代此项。复用同版本有效证据，不新增确认环节或重复报告。

- 选取同一记录，按已确认业务语义核对来源数据或业务快照、实际接口响应与页面关键字段，检查名称/关联、枚举、数量/单位、日期及明细等本次受影响内容。历史快照与当前主数据不同可能合理，应按契约判断，不能仅以接口和页面一致认定正确。
- 对异常空白、占位符（如 `--`）、错误值或格式追到具体环节，区分源数据确实为空、当前状态不适用、接口缺失和展示映射错误；零值等有效值不能误判为空。没有依据时记录未核实，不能推断为正常或补造业务值。
- 每类独立展示逻辑至少用有代表性的非空数据核对，空值/不适用状态按实际风险覆盖；不能只凭全空样例通过。按影响检查滚动后内容、横向列、折叠区域、附件及切换记录后的残留值，不穷举无关组合。
- 简记样本标识、关键预期/实际差异及证据，正常项概述即可。实现问题在已有授权内修复并复测；源数据问题说明影响，按统一授权处理，不为验收通过修改原有业务数据。关键展示字段仍有无法解释的错误或缺失、必要样本无法取得时，相关页面验证不得标为通过，并给出具体缺口和下一步。

## 开发环境测试数据与菜单

数据库环境遵循 [数据库环境](coordination.md#数据库环境)，默认复用现有开发库。运行数据库测试前检查初始化、清理和迁移脚本；不得把带删库、重建业务表、全表清空或无范围删除的隔离测试直接指向开发库。测试数据仅限本任务可识别且可安全清理的记录；无法满足时调整用例或报告该项验证缺口，不自行另建隔离库，不为测试通过破坏原有数据。

已确认开发环境中，现有数据足够且来源符合验证目标时只读复用；新增真实联调或验收数据必须按下述“缺数据先查业务链路”规则，通过已授权的正常业务流程产生。记录数据来源、操作路径、唯一标识、关系、状态和清理方式；不得以合成数据授权修改既有业务数据、覆盖冲突 ID 或触发未授权的发布、审批等效果。

准备、验证、清理按交付阶段推进；正式业务开发默认保留验收所需数据至用户明确验收通过，或明确免除人工验收且满足其他收尾条件后再清理。删除前核对归属、预期状态和新增关联。已被他人修改/引用或不能安全删除时只暂停该项清理并说明，不能扩大删除；结束后验证清理结果及原有数据未受影响的证据。直接清理数据的 SQL 仍由用户按数据库环境规则手动执行；清理授权不包含补造或改写业务事实。

### 缺数据先查业务链路

1. **先查为什么没有产生数据。** 沿目标数据的业务生产入口、前置条件、权限、审批、状态流转、事务写入和关联关系做必要只读核查，区分流程尚未操作、生产链缺陷、上游能力未实现、历史数据异常和测试种子。已有数据是否满足验证，须看业务来源和状态，不只看表中是否有记录。不能直接把“缺样本”解释成需要补数。
2. **用正常流程产生验证数据。** 真实联调及业务验收必须通过正常页面操作或等价的公开业务接口完成所需步骤，保留身份、校验、审批、状态流转及事务约束。调用业务接口不能跳过待验证的上游步骤；验证页面交互时也不能只用接口成功代替页面操作证据。测试名称、备注等输入可使用可识别的测试标记，但轮次、资格、审批结论、发布状态、关联关系、附件和提交时间等业务事实必须由对应正常流程产生，不得直接插表、改状态、手工拼关联或伪造附件补齐。
3. **流程不通就处理根因。** 生产链有缺陷时，在授权范围内修复入口并从正常操作复验；上游未实现、前置条件或权限不足时，说明具体缺口及影响，超出范围则先申请增量方案授权。继续独立可验证部分，将受阻部分如实标为未验证；不得为了让测试走通增加测试专用写库入口、跳过审批或补造业务事实。
4. **合成数据授权不包含伪造业务过程。** 默认授权仅覆盖已批准开发环境及操作范围内，通过正常流程创建的可识别测试记录，以及不写入共享业务库的单元测试 Mock/fixture。离线或隔离测试替身只能支持相应局部结论，不证明真实业务链路已完成；不因此自行新建数据库。历史种子数据不得冒充真实提交、审批或发布证据，也不得补字段使其看似经历过完整流程。
5. **历史修复与验证准备分开。** 只有业务上确实需要恢复历史记录，且已查明根因、历史事实有证据，才提出独立的数据修复方案，说明目标记录、事实依据、影响、核验与回退并取得专门授权。没有历史业务事实不能用回填制造它；需要 SQL 的仍由用户手动执行。用户执行 SQL 的确认只证明执行完成，不使补造数据成为合法验证依据，也不能把历史修复包装成继续联调的必经步骤。修复结果与正常流程验证分别报告。

已确认功能范围内的菜单直接按项目方式落实，先查是否已存在，作为正式配置保留，不随样例删除，也不顺带修改角色权限或其他菜单。结构变更、既有数据修改、生产操作等按统一授权规则处理。

## 缺陷与证据

缺陷记录必要的前置条件、复现、预期依据、实际结果、影响与证据，区分实现、测试、环境和需求问题；同根因集中报告。已有修复授权持续有效。修复后复核实际变化，复测原失败场景及相关影响；仅新变化、失败或证据缺口扩大检查，不重跑未受影响的全部回归，不删除断言或放宽契约求通过。

按实际相关端和检查项记录通过、失败、未验证或不适用，附范围、版本、环境及依据；无需为每个维度另建报告。核实测试是否实际启用、失败/跳过情况，不能只看退出码；既有失败只查与当前结论的关联，无关问题记录后停止扩展。

## 工程完成与人工验收

工程完成条件：确认范围已实现或有复用依据、契约一致、必要项目规范与工程检查通过、适用真实联调/功能/视觉验证完成、影响完成条件的问题关闭。由当前证据支持结论，不因用户未回复就撤销工程完成事实。

**正式业务开发默认必须经用户人工验收通过，才能合并或回写开发基线。** 仅用户明确免除人工验收时可跳过；未约定、未回复、批准实施、允许联调、完成登录或 SQL 执行、代理自测通过，都不构成验收通过或免除。记录用户原意、适用任务范围及待验收版本；泛泛的“继续”不能替代明确验收结论，有歧义时只澄清该关口。

**合并关口按实际效果判断**：Git merge、cherry-pick、文件复制、补丁应用、增量回写等，只要把任务成果整合到原开发目录或目标基线，都须先满足人工验收关口，不能因未产生 Git 提交而跳过。任务隔离目录内的开发、自测和已授权修复可继续，不因此阻断必要验证。

人工验收是正式业务开发的默认交付关口，无需询问用户是否增加；主控须将该条件及当前状态随任务简报传给执行者。开发、自测及必要审核完成后报告“工程自检完成，待人工验收”，保留验收浏览器标签页、前后端及必要依赖服务、worktree 和所需测试数据；不得因本轮回复结束就关闭、停止、删除或提前合并。提供可直接打开的地址、简短验收路径、样本及已知限制，确保展示的是待验收版本，明确真实数据与测试替身的区别。记录进程与端口等恢复信息，不承诺服务永不退出；环境中断时在已有授权内恢复，不让用户重新配置启动。

等待期间不重复审核测试，不把沉默当验收通过。用户反馈问题后在授权范围修复、针对性复测并保留环境供复验；用户明确通过，或明确免除人工验收且工程条件满足后，按已确认方案自动连续执行提交、合并或回写、远程推送、远程核验及清理，无需逐项再问。验收通过或免除均不覆盖原有“不提交/不推送”等限制，也不授权新的操作范围。验收后若实质改变已验收行为或契约，修复并验证后对受影响部分重新交付人工复验，除非用户明确免除的范围涵盖该变化；不把旧版本通过无限沿用到新变化。

仍有独立可执行工作继续做；只剩已核实外部条件或增量授权阻塞时，按协调规则给出明确请求和恢复点，报告部分完成，不将未验证记为通过。用户要求只交阶段成果时准确注明边界。

### 同步交付代码验收

**提交用户人工验收时，同一条交付消息须同时提供功能验收和代码验收材料**，不能只给页面地址、自测通过结论或文件名清单。详细内容复用同一主记录和已有审核证据，不另建重复报告。

- **可查看的实际差异**：标明仓库、任务目录/分支、比较基线及待验收版本，提供可直接打开的 diff/审核入口。无现成入口时提供完整差异文件或可直接执行的准确查看命令；覆盖本任务已提交、暂存、未暂存及未跟踪的新文件，排除无关改动。未提交内容说明其状态，不能只用 HEAD 代表待验收版本；不得为生成审核入口擅自提交、推送或创建 PR。
- **代码阅读指引**：按业务变化概述关键文件与实现入口、设计取舍和影响范围，给出可定位的文件链接或行号，帮助用户检查代码质量。重点按实际风险覆盖职责与分层、可读性、重复逻辑与复用、项目规范、异常及边界处理，以及相关安全、性能和可测试性；不要求所有任务填满固定检查表。
- **质量审核结论与证据**：区分开发者自查、独立审核和用户代码验收，说明实际审核范围、发现及修复情况、未解决问题、必要验证结果与未验证项。复用同版本有效证据；未发现问题不能表述为保证无缺陷，功能测试通过也不能替代代码质量结论。

功能验收与代码验收属于**同一个人工验收关口**，集中请求用户确认，不拆成两轮固定审批。完整展示两类材料后，用户明确整体“验收通过”可覆盖两者；用户只确认功能或只确认代码时，记录对应结果，另一项仍待验收，除非用户明确免除。已有明确覆盖两者的验收或免除继续有效，不重复索取。

验收期间发生代码变化时，同步更新实际差异、版本标识和受影响的审核结论，向用户说明复验范围；纯代码质量调整也不能沿用变更前的代码验收结论。未受影响的功能或审核证据继续复用，不因此重跑全量验证。

## 合并后先推送再清理

**代码合并后，必须先将合并结果推送到已核实的远程目标分支，并确认远程包含本次交付提交，才能删除本地任务 worktree、临时分支及必要恢复资料。** 推送的是合并后的目标分支，不能以任务分支已推送代替；远程已包含交付提交时只核验，不重复推送。

- 将远程仓库、目标分支、推送及清理范围纳入统一方案的完整收尾清单。**方案获实施授权后，推送即属于已授权收尾；人工验收通过后自动合并、推送、核验并清理，不再单独申请推送授权。** 验收通过用于满足执行关口，不需再次授予方案已有权限。仅新增范围、目标发生实质变化或已有明确限制时按统一授权规则处理；用户明确不推送时保留相关本地资源，除非用户明确允许本次仅本地交付并清理。
- 推送后读取远程目标分支，核验交付提交与远程提交一致，或交付提交已包含在远程历史中；不能仅凭本地跟踪引用或推送命令退出码认定远程已保全。远程已有后续提交时，不要求远程分支头与本地完全相同。
- 推送失败、被拒绝、目标不明或无法核验远程结果时，暂停受影响仓库的清理，保留 worktree、任务分支及必要恢复资料，报告原因和恢复点；不得强制推送、重置或先删除再补推。跨仓库逐一核验，分别报告状态。
- 用户明确要求不提交的增量回写，不为满足推送条件擅自提交。未提交成果无法通过推送保全，默认保留相关资源；只有用户明确允许本次仅本地交付并清理时，才可按下述内容保全与安全清理条件执行。

## 提交合并与自动清理

工程条件满足且人工验收已明确通过或被用户明确免除后，核对拟提交内容归属、当前证据版本和目标分支，只提交本任务增量并按 [分支规则](coordination.md#分支与运行环境) 合回开发基线。目标变化只补相关集成核验；冲突、其他改动可能被覆盖、必需检查失败或证据不足时暂停受影响合并，不强制覆盖或降低条件。跨仓库分别报告成功与剩余项，不将部分成功当全部完成。

按已授权方式完成合并或增量回写后，核对目标结果与必要集成证据，并满足[合并后先推送再清理](#合并后先推送再清理)的远程保全条件或用户明确授权的例外。用户要求不提交时不得为了清理而提交；回写只包含本任务增量，保留目标中的并行修改。清理前的必要记录暂存于工作树外；按下列保护条件在已有清理授权内移除本任务 worktree 和临时分支，并按 [证据与备份清理](#证据与备份清理) 清理不再需要的过程文件：

1. 证明成果已完整合入或回写目标；压缩合并不能仅靠祖先关系判断，未提交回写须核对文件清单及实际内容差异，目标有后续改动时检查是否保留任务成果。检查暂存、未暂存、未跟踪和忽略文件，独有资料先按授权保留，不把 Git 状态干净等同于没有独有文件。
2. 确认无其他任务或服务依赖；核实身份后仅停止本任务占用进程。核验解析后的绝对路径及链接目标，本步骤仅移除任务代码子目录，不删除原始工作区或目标分支目录；主记录任务目录须在下节归位与核验条件满足后单独清理。指向主目录的 Junction/符号链接只解除链接，不递归进入目标；删除前后核对主目录和共享依赖的必要保护证据。
3. **以成果是否保全判断清理条件，不以是否执行 Git commit 判断；同时须满足上述远程保全条件或用户明确授权的例外。** 宿主管理的 worktree 使用其归档能力；手动 worktree 在验收、整合及上述保护核验满足后使用 Git 移除。若仅因已保全的未提交内容需要 `git worktree remove --force`，在已有清理授权内可直接对已核实的本任务绝对路径执行，不重复确认，也不为清理擅自提交。核验须覆盖带入的原有依赖、暂存、未暂存、未跟踪和忽略文件；临时验收配置及产物确认仅供本任务且不再需要后可随工作树清理，不能将未知差异一概当临时文件。再安全删除本任务临时分支，保留目标、其他分支和远程分支。此许可仅针对 Git 的未提交状态保护，不授权绕过审批、访问控制或其他安全拒绝，也不授权硬重置或递归删除替代被拒绝的操作。
4. 逐仓库检查移除命令的退出码及错误，分别核验 worktree/分支登记和磁盘目录；不能用后一个命令成功掩盖前一个失败。登记已移除但目录仍在时报告残留，不能宣称删除完成。存在未保全的独有内容、未整合成果、归属不明、服务依赖或实际安全拒绝时，保留受影响工作树并说明具体原因；不能仅以“有未提交内容”作为停止清理的理由。用户明确要求保留或暂不删除时不清理；遇审批拒绝不得换工具、换命令或提升强制程度绕过。

统一根目录下的本任务仓库 worktree 全部安全移除后，核验任务父目录无残留文件、链接及其他任务或服务依赖，才删除空的任务目录。**不删除共享 worktree 根目录、项目分组目录或其他任务目录**；有残留时记录实际路径和原因，不递归删除父目录代替逐仓库清理。项目内的主记录任务目录按下节条件清理，不因 worktree 已移除而提前删除。

满足条件即收尾，不重新开发、全面审核测试或扩充重复归档。交付只突出结果、必要证据、实际剩余问题以及提交合并、远程推送及清理状态；推送遵循上述授权与核验规则，不自动部署。

### 清理分步执行与分别核验

**首次安排清理时就按对象和依赖拆分执行，每步成功并核验后才进入依赖它的下一步。** 每次写操作调用只处理一个清理对象；停止服务、移除 worktree、删除临时分支、删除空父目录和删除过程目录不能串成一个组合命令，也不把多个仓库的删除放入同一次调用。已有授权沿用，拆分执行不新增审批。

- 先核实并停止本任务服务，确认相关进程或监听已释放。移除单个 worktree 前，完成上述内容保全、归属、绝对路径及链接核查，从该 worktree 之外执行移除；返回后立即检查该操作的退出码或工具结果，再以独立只读调用核验 worktree 登记和磁盘目录均已移除。
- 该 worktree 移除核验通过后，单独安全删除对应临时分支，再核验分支引用已不存在；不删除目标分支、远程分支或其他任务分支。多个仓库逐个重复，分别记录结果。
- 全部相关 worktree 清理完成后，重新核验本任务父目录确为空且无依赖，单独删除该空目录并核验路径不存在；过程目录在满足下节归位与保全条件后另行删除并核验。不得递归删除父目录代替尚未完成的子项清理。

失败时保留已完成步骤的事实，只暂停失败步骤及依赖步骤；恢复前先只读核实现状，不重复删除已不存在的对象。区分工具执行前的策略拒绝、Git 返回错误和目录残留，记录实际报错与恢复点，不从组合调用的最后一个退出码推断全部成功。**遇审批或安全策略拒绝，停止受影响删除；不得将已被拒绝的操作拆分重试、换工具或改写命令以绕过限制。** 分步规则用于事先缩小操作范围和定位结果，不能保证消除策略拒绝；仅返回 `blocked by policy` 时如实报告原因未明，不猜测为文件占用、未提交改动或用户未授权。

### 策略拦截后的手动清理交付

**清理被策略拦截后，完成必要只读核查，直接向用户交付手动清理清单。** 不为收尾修改或引导用户调整全局审批、沙箱或安全规则，不默认要求切换会话权限、重启客户端或反复重试；用户另行明确要求排查权限时，才进入对应排查，不能以清理授权代替权限配置变更授权。

清单在同一条交付消息中自包含，列出以下实际内容；无对应项时简述“无”，不虚构路径或保全结果：

- **需要保留的文件**：逐项给出准确绝对路径、用途、保留原因及已归位位置或建议保存位置；区分已保存与待用户保存。仍在待删目录内的必要文件，明确要求先保存并核对完整，再删除目录。不得把被拒绝组合命令中计划执行的备份当成已完成。
- **可手动删除的目录**：只列已核实归属、内容及依赖的本任务准确绝对路径，说明是空父目录还是过程资料，并标明“可直接删除”或“完成上述文件保留后可删除”。优先给资源管理器操作指引，不提供扩大范围的通配删除；不得包含共享根目录、其他任务或尚需保留的独有成果。
- **暂不能删除的对象**：存在未保全内容、运行依赖、链接目标不明或 Git worktree 登记尚未移除时，单列对象、原因及解除条件。仍登记的 worktree 不当作普通目录建议直接删除；需按其管理方式处理，避免留下失效登记或误删共享内容。

最后分别说明已完成清理、待用户手动处理及未核实事项；未经用户反馈或后续只读核验，不标为全部清理完成。保存 SQL 文件不代表执行 SQL，删除本地目录也不代表清理数据库样本；相关数据沿用用户已确认的保留或清理要求。此交付不授权代理绕过拒绝，也不要求用户再次批准已授权的整个收尾范围。

## 证据与备份清理

**人工验收通过、合并或回写完成并核验，且满足上述远程保全条件或用户明确授权的例外后，必要长期资料先归位，默认删除整个 `.codex/workflows/<任务标识>/` 任务目录。** 用户明确免除人工验收时，沿用该免除范围，其他条件不变。先安全移除关联 worktree，确认无服务及其他任务依赖，再清理主记录目录；不能通过删除主记录目录跳过嵌套 worktree 的安全移除。清理属于已授权收尾的一部分，不逐项重复申请；不再默认永久保留 plan.md 或 evidence，也不能只因验收通过便提前删除回写保护资料。

- **长期资料先归位**：正式迁移/恢复 SQL、使用说明、必要契约及项目要求留存的材料，放入项目已有规范目录；已有相同有效内容则引用，不重复复制。核对归位内容完整、可读且引用有效，不覆盖其他改动，不通过另建一个完整任务备份目录变相永久保留全部过程资料。用户指定的长期共享文档位置不作为可整体删除的临时任务目录；归位需要新增未授权范围时只暂停相关清理。
- **交付摘要留在目录外**：在当前会话或已有且获准写入的提交/交付记录中，保留最终范围、用户验收通过或免除依据、交付版本及目标、验证结论与未验证项、已知限制、整合及清理结果。未提交回写保留必要文件清单及校验摘要；较长材料放项目既有合适位置。不能只把摘要留在即将删除的 plan.md，也不为保存摘要擅自提交、推送或发送到其他会话。
- **备份与未解决事项单独核验**：确认成果完整、原有及并行修改保全，且不存在未解决问题、待复验证据、独有成果或必要回退资料，再整体删除。未提交回写不能假定 Git 能恢复；备份仍是唯一必要恢复来源时保留该任务目录，说明具体原因和解除条件，不为了删除备份擅自提交。用户明确要求保留的材料继续保留，不用清理掩盖失败或验证缺口。
- **限定整体删除范围**：逐个核验本任务目录归属、完整清单（含隐藏、忽略文件）、解析后的绝对路径及链接目标，确保确切目标是该任务目录而非 `.codex`、`workflows`、项目根目录、共享 worktree 根目录或其他任务。符合条件后删除该任务目录及内部方案、日志、截图、临时文件和已无用途的备份；不跟随 Junction/符号链接进入其他目录。同步改写外部记录中指向已删文件的链接，保留资料改指归位位置。
- **核验结果与例外**：确认长期资料可读、应删任务目录确已不存在，分别报告 worktree 和主记录目录清理结果。归属不清、依赖未解除、资料未安全归位、用户要求保留或安全操作被拒绝时，仅暂停受影响任务的删除，说明原因与解除条件，不绕过拒绝。规则更新不自动授权批量清理现有历史任务目录，也不安排未经请求的定时删除。
