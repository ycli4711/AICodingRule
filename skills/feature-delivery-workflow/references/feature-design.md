# 当前功能的需求、接口与实施计划

用于当前功能实施前的设计和范围变化。先给用户可理解的行为，再给必要技术细节；复杂度决定表达深度，不机械填写整套表格。

## 需求与功能清单

- 保留用户原始目标及来源，区分已确认事实、建议和待定规则。一句话足以开始分析。
- 先核查当前工程中可复用能力及约定，再问会实质影响结果的问题。没有原型不等于没有设计依据。
- 每个功能是可独立验证的业务结果，记录相关端、依赖和完成条件。后台接口、界面文件或单个输入框不自动等于一个业务功能。
- 当前功能方案只覆盖它自己的有效范围。其他功能继续留在队列；不同案例或历史运行的操作、字段、授权不得混入。

先建立按原型目录到页面层级的可点击索引，再按可独立理解和确认的用户场景组织内容，拆分依据与导航、审查分组的区别见 [运行记录](run-records.md)。同一场景的需求、交互、数据、规则和验收标准集中说明；不按预设页面或操作清单套用，也不用一份全系统接口表代替需求确认。已有核查可复用并注明来源和未验证部分；仅重新排版不意味着重新验证或业务确认。

按“定义并确认需求 → 设计并确认接口及接口逻辑 → 制定实施计划 → 实施确认 → 开发”推进。每阶段只针对当前明确范围，前阶段关键缺口未闭合或未确认，不进入依赖它的下一阶段。已有有效确认继续沿用，不因换阶段或加载 Skill 重复确认。

阶段推进应对用户可见：审查回复明确当前阶段、当前项和下一步；跨阶段前汇总该范围的确认结果与缺口，说明目标阶段和进入依据。短答的解释遵循 [运行记录](run-records.md) 的低负担反馈规则，不能仅凭“继续”将需求记为已确认并生成接口草案，也不能将接口审查直接推进为实施计划或开发授权。

现有接口、代码和工程能力可提前只读核查，用于发现限制与差异；这些是可行性证据，不是需求定义或已确认设计。需求未确认时不展开正式接口设计或实施任务清单，不因接口缺失而擅自删减需求。技术资料链接回对应页面，用户无需在聊天阅读全文。

## 第一阶段：需求定义与确认（包含交互）

先回答业务问题：谁使用、要完成什么、操作后应发生什么。围绕当前审查单元说明字段含义与业务校验、状态与权限规则、异常反馈、范围和验收标准，关联来源页面或业务能力。权限先表达“谁在何种条件下可以做什么”，不要求用户在此阶段确认权限编码、接口参数或实现类。纯服务任务同样先定义调用方目标及可验证的业务结果。

客户端角色在编码前参与；主控汇总给用户。按独立操作描述触发、可见结果、数据需求、适用校验和状态。

| 有何依据 | 怎么处理 |
| --- | --- |
| 可交互原型 | 核查任务内关键操作及结果，等价入口可取代表；标明已核查、未核查或无法进入 |
| 截图或设计稿 | 分析可见布局和信息；未显示的交互提出建议，不能写成已观察事实 |
| 只有文字 | 查现有产品和组件约定，给出操作方案；必要时提供草图供审查 |
| 纯服务任务 | 交互部分标不适用，仍明确调用方和业务结果 |

核对当前功能适用的加载、空数据、成功、失败、无权限、回填、取消与防重复操作行为。按平台核对必要差异，不强求所有端布局完全相同。

关键字段先说明业务含义、展示位置、用户输入或业务来源及保留规则；接口字段路径、类型映射和读写方式在第二阶段展开。提前读取已有契约所得限制以待协调差异记录，不冒充已确认需求。静态内容注明来源，不虚构 API。

原型与工程能力存在实质差异时说明选择及影响，不擅自删字段或操作。未核查内容不包含在整项“已确认”结论中。制作需要写文件的交互演示时，先核对其具体授权；演示确认不自动授权业务实现。

需求输出：当前场景目标、使用者、交互与业务规则、关键数据需求、验收标准及实质差异。重要未定事项集中澄清，再请用户确认该范围的需求，记录版本和确认依据。对单个问题的回答只更新该项，不自动代表整个审查单元已确认；单元确认也不代表整个页面或系统已确认。拆分后的单元若依赖未决的公共规则，明确受影响范围，不能用分组绕过下一阶段的进入条件。已确认规则不再重复询问。

## 第二阶段：接口及接口逻辑设计与确认

进入条件：当前范围的需求已获确认。服务端与调用端基于该版本需求共同设计，优先读取实际路由、契约来源、调用封装和项目规范；原型样例不能证明服务端规则。

### 接口设计文档的阅读顺序

每份文档围绕当前审查范围，标明状态、需求版本，提供可点击目录和返回需求或索引的链接。默认按以下顺序组织，简单内容可合并，不机械增加章节或文件：

1. **审查摘要**：用一句话说清本次目标，重点只列变化、实质问题和待决策项。修订时先说明相对上一有效版本的差异；纯复用且无差异的接口不逐项列入摘要。将阻塞定稿的问题放在开头，不让读者读完长文才发现缺口。
2. **接口定义**：逐个接口集中说明用途、请求、响应、权限、错误、调用端映射和核心业务逻辑。每个接口先用简短业务语言解释操作与结果，再给技术契约；不另写一遍全量业务说明。
3. **关联依赖**：只说明支撑本次契约所必需的其他接口及行为变化。已有外部契约不变时引用原契约，仅写本次行为差异；新增或变化的契约仍须完整定义，可链接其唯一正文。
4. **数据库改造摘要**：涉及数据结构或存量数据变化时，在正文用简短表格说明改哪张表、哪些字段、用途和历史数据处理，具体边界见下节；不只写“保存快照”等结果描述。无改造时一句话说明，无需空表。
5. **资料链接**：按需链接需求、技术依据和核查证据，不在末尾附整段工程记录。

### 重点与内容边界

- **按差异展开**：已确认且未变化的内容引用有效版本或唯一正文，不重新解释或要求审核。已核实、无差异的常规处理用一句话说明沿用哪项现有约定，例如“认证与分页包装沿用现有采购接口约定”，并提供可定位的来源。核查过程不进入审查正文；必要证据仍按运行记录保留。没有依据的内容不能按“没有问题”省略，精简说明不等于省略核查。
- **短句先给结论**：摘要一项只说一件事，用“变化”“待决策”“待核查”等短标签区分。决策项写“建议怎么做、影响什么”；核查项写“缺什么、影响哪项契约、如何核实”。详细规则链接正文，不在摘要堆叠背景、类名和防御性解释。没有对应事项就省略，不凑固定数量。
- **决策与核查分开**：用户决定业务取舍，工程事实由主控取证。关键契约未定时标明受影响接口暂不能定稿，不能用“待核实”字段充当完整契约，也不能把整个接口设计包装成可确认状态。
- **规则只完整定义一次**：字段约束放字段表，复杂状态映射放状态表，跨字段处理规则放核心逻辑；其他位置引用。不要在业务说明、审查事项、字段表、兼容说明和验证条件中反复复述同一规则。
- **正文保留契约判断所需内容**：数据含义、权限与可见范围、成功和失败结果、状态变化、必要副作用、历史数据语义及兼容影响。事务、幂等、并发仅在影响调用方可观察结果时说明保证及边界；底层机制有审查必要时链接技术依据。
- **数据库设计保留摘要**：列明表名（必要时含库名）、字段名及新增/修改/删除动作、类型与可空/默认值、业务用途，以及旧记录保留、回填或转换的处理原则。历史规则已有唯一正文时直接引用。区分拟议设计与已核实结构，未确定项标出缺口，不猜测字段。数据结构变化属于接口设计的审查内容，不能随迁移执行细节一并删去或仅藏在核查记录中；开头审查摘要用一句话提示数据库影响并链接本节。
- **实施与证据各归其位**：迁移脚本、执行批次与顺序、回填操作步骤、性能索引分析和 EXPLAIN、具体锁顺序与代码组织、发布和回退步骤、构建命令及测试执行清单不进入接口正文。影响契约的唯一性等数据约束仍保留在数据库改造摘要中。核查过程、源码路径清单和工程基线放关联记录；迁移执行细节及其他实施安排到实施计划阶段再制定，不为清理正文提前生成下一阶段产物。影响契约的实质风险仍在摘要或对应接口中简述，不能随细节一起隐藏。
- **交付前检查阅读效果**：只看开头应能知道改什么、卡在哪里、需要决定什么；只看某个接口应能找到它的完整契约与核心逻辑。删除重复解释和无关章节，同时保留开发对接所需信息，不能为缩短篇幅省略关键约束。

摘要与契约必须一致；新增建议若改变已确认业务规则，先回到受影响需求处理。设计草案不替代需求定义，也不提前编排下一阶段的实施任务。

接口阶段的聊天仍简短说明当前阶段、当前审查项链接、需要用户判断的实质决策和下一步，技术细节留在文档。需要确认的是可审查的接口设计范围及其行为，不要求用户逐项批准开发人员可依据现有规范决定的实现细节；涉及重要兼容、数据或副作用变化时应说明影响并取得相应确认。

### 契约与逻辑的必要内容

| 类型 | 提交审查的内容 |
| --- | --- |
| 新增接口 | 方法、路径、用途、调用方；请求位置与字段、类型、必填/默认及约束；响应结构、类型、可空与含义；权限、适用错误结果和核心逻辑 |
| 改变契约 | 原约定与变化、调用端影响、兼容处理、必要数据或副作用差异 |
| 复用已有接口 | 已核实的契约引用、当前功能的调用与字段映射，不重复全量定义 |

新增接口保留必要完整定义；变更接口写清差异并引用未变部分，使正文与引用共同形成可用契约，不用总览替代变化内容。共享包装、常规错误及未变化的公共类型按上述差异规则简述引用；新增、变化及关键使用字段不能因“逻辑明确”而删去或以“沿用约定”笼统代替。数据库定义同样保留。分页、日期、ID、枚举、精度按实际项目核对，只有差异或问题才另作解释。复杂状态、事务或副作用顺序才展开必要图示或伪代码。

请求参数从哪个输入或状态产生、响应如何影响界面，应能与交互一一对应。没有来源或约定相互冲突时，标出具体缺口及影响，先核查或澄清，不能用类名或“按现有约定”掩盖问题。

核心逻辑说明字段表之外的后台校验、权限检查、状态变化、数据读写及必要副作用；失败结果统一放在该接口的错误说明中。异步操作区分请求接受与业务完成。实现深度遵循上述内容边界，已有能力优先复用。每项逻辑应能追溯到已确认需求，不借技术设计增加业务规则。

接口输出遵循上述阅读顺序。必要的契约示例或结果判定条件就近放入对应接口，不再复制规则生成全套验证清单。关键缺口闭合后请用户确认接口及逻辑；收到有效确认后才能制定该范围实施计划。复用已有接口可用准确引用及适配结论简述，纯本地功能无接口时说明不适用依据，不虚构接口。

项目明确要求通过特定资料源取证时遵循该要求。没有这项约束的项目可使用可核实的契约来源，不把某个 MCP 工具设成全局前置条件。

## 第三阶段：制定实施计划与实施确认

进入条件：当前范围的需求、接口及接口逻辑均已确认；无接口的任务已说明不适用依据。引用有效版本制定实施计划，不提前生成依赖未决规则的可执行任务：

1. 用户目标、业务结果和适用验收条件。
2. 已确认需求（含交互）、接口及逻辑的版本和来源，以及对应关系。
3. 相关端、工程与必要修改范围；已有能力复用依据。按 [协调规则](coordination.md) 明确可并行任务、执行者及必须等待的条件，区分开发与联调依赖；采用串行时说明具体原因。
4. 步骤、依赖、分工、实际风险和关键疑问；涉及数据库改造时引用已确认的数据设计，补充迁移脚本范围、执行顺序、必要回填、验证与回退安排，数据库实际执行遵循其明确授权。
5. 工程检查、真实联调、各端功能和视觉验证方式，及环境与操作边界。

计划形成后提交用户审查具体实施范围，获实施确认再写业务代码或建立工程骨架。需求确认、接口及逻辑确认、实施授权按顺序分别记录，不默认合并为一次确认，也不凭局部口径回答跨过阶段。已有同一范围的有效确认和授权无需重新取得。

契约变更若影响已确认交互，更新受影响方案及用例，按授权判断是否需补充确认；未经批准的建议不能成为新执行基线。其他独立、仍在有效范围的任务继续。
