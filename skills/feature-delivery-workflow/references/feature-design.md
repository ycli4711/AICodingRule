# 方案与授权

## 技能启用边界

- 本套五个技能仅在用户明确要求使用对应技能时启用（`$技能名` 或明确点名要求使用均可）。普通的开发、修复、审核、测试请求，以及“可以，按方案实施”等实施确认，不构成技能启用指令；仅讨论、检查或修改技能也不构成启用。
- 用户明确启用 `feature-delivery-workflow` 后，可在该任务范围按需使用其四个配套角色，无需逐个再次点名。单独点名某个角色只启用该角色及其必要参考，不自动启动整套工作流或其他角色。
- 未明确启用时，不通过其他技能、参考链接或历史调用间接套用本套规则。继续遵循用户指令与项目规范；不能仅依据本套规则创建或切换分支、创建 worktree、分派代理或安排提交合并。
- 整套工作流的任务分支/worktree 及协调安排仅在用户明确启用 `feature-delivery-workflow` 时适用；单独启用角色不自动引入这些安排。单独使用角色不自动取得整套收尾职责。
- 仅启用技能不等于批准具体方案；方案确认后的完整收尾授权统一见[唯一授权规则](#唯一授权规则)。

## 需求与统一方案

先核实使用者、目标、范围、关键交互、数据与业务规则，区分已确认事实、建议和缺口。已有明确需求不重复审查；关键口径不足时集中澄清。原型只证明实际观察到的行为：核查任务内独立关键操作及结果，等价入口取代表，未核查内容不能写成已确认。没有原型可依据现有产品和有效资料，不虚构行为。

需求确认后，必须先交付一份可点击的完整设计与实施方案文档，取得针对该文档的明确确认后实施，具体执行下文“方案文档交付与实施关口”。同一主方案按功能逐项展开，接口和计划归入所属功能，不因分章增加审批。仅重大未决问题、需先验证可行性或用户明确只做设计时拆开，并指出具体影响；已有有效文档和对应确认保留引用，不为新流程重排或重审。

以下是方案需要覆盖的内容，不是必须依次填满的章节模板；呈现顺序按下文“阅读层次与版式”组织。按实际复杂度保留：

- **审查摘要**：一句话目标，重点只写变化、问题、待决策项和主要影响；常规已核实内容一句话带过。
- **接口与核心逻辑**：新增契约保留方法、路径、权限、请求/响应类型与约束、错误及必要业务逻辑；变化契约说明差异并引用未变部分。字段、状态规则只定义一次；异步接受与业务完成分开。接口事实依项目要求核验，不把某个工具设成通用前提。
- **数据与调用端影响**：涉及数据库改造时说明表、字段、类型、可空/默认值、用途和历史数据处理；前端接入说明必要新增/修改文件、作用、接口映射及联调条件。无变化简述即可，不造空表。
- **实施与验证**：修改范围、依赖与并行分工、操作清单、风险及完成条件。迁移执行顺序、回退、命令和测试安排放这里，不混入契约正文。文件清单与业务规则引用前文，不复制。分支与环境遵循 [执行协作](coordination.md)，检查范围遵循 [验证与收尾](acceptance.md)。

必要定义不能为缩短篇幅省略；未知信息不能当成常规无问题。工程事实由执行者核查，用户决定实质业务取舍，不逐项询问实现细节。

### 原型偏离关口

依据可交互原型、截图或设计稿实施时，以已核查的参考及用户已确认的差异为基线。**接入真实数据或批准整体实施，不等于授权重新设计原型。** 只确认开发范围、后台能力或业务规则，也不能推导出对未展示的原型差异的批准。

1. **先核对原型与拟议实现。** 覆盖本次涉及的字段及含义、表格独立列、信息层级、操作入口、操作顺序、状态反馈与关键布局；可交互原型还需核查关键操作的可见结果。注明参考位置和已核查/未核查状态，不能用代码推测替代交互核查，也不能将缺少证据的行为写成已确认。
2. **实质偏离先展示并确认。** 删除、隐藏、替换或合并原型字段/表格列/操作，改变信息含义、关键流程、信息层级或关键布局，均须在完整方案中逐项写明“原型行为 → 拟改行为 → 原因与影响”，保留可定位的参考，并在聊天摘要明确突出差异。初次方案可将这些差异纳入同一次方案授权，不另设重复审批；只有差异已明确展示且用户确认覆盖该差异，才能实施。实施中新增偏离须先更新同一方案并申请对应增量确认，不能沿用未包含该差异的旧授权。
3. **后台缺口不能自动改写产品。** 缺字段、缺接口、模型不同或实现成本较高，先记录真实缺口，提出保留原型所需补齐与必要替代方案及影响，交用户选择；不得自行删列、合并列、隐藏操作或用另一业务字段替换原含义，也不得伪造数据。新增状态或数量展示有业务依据，仍不自动授权重排原型结构。
4. **实现与交接守住已批准差异。** 主控和执行者使用同一差异清单与确认依据。发现未批准的偏离时暂停受影响改动，继续不依赖该决定的已授权工作；若已写入，如实列出实际差异，保留现场供审查，不擅自回滚，也不以事后文档或测试通过追认授权。

保持语义、操作及关键结构的实现细节，以及已批准的响应式适配，不逐项增加确认；用户明确要求的具体调整直接按其范围执行。未明确授权时，不能以“优化”“适配真实数据”或“组件重构”为由豁免实质偏离。方案中已有明确批准的差异继续有效，不重复询问；差异选择不替代尚未完成的完整方案实施授权关口。

### 疑问单独交给用户，工程事实先自行核实

需要用户回答的业务选择，在聊天交付中以“❓ 待澄清”或“🔀 待你选择”集中单列，并通过可用的用户输入工具提问；工具不可用时直接在聊天中提问。每项写清问题、推荐选择及其影响，不能只埋在文档中、写成“方案另建议”，或只给完整方案链接。文档保留同一问题的依据和状态，聊天保留足以直接作答的摘要，不要求用户翻找正文。

只列仍需回答的事项；已确认口径沿用。可自行核实的工程事实先按 [只读核查](coordination.md#只读核查与任务关联性) 查证，不转交用户猜测。业务选择与实施授权分开表达，回答局部问题不等于批准整份实施；关键选择影响方案时先澄清，其他问题可在同一条消息中明确列出，但不能让笼统的“确认方案”掩盖未展示的取舍。

### 发现事项先判断与目标的关联

把发现纳入问题、阻塞或实施范围前，说明它影响哪个已要求的行为、依据是什么，以及不处理会造成什么结果。区分目标功能、实现目标所必需的直接依赖、相关性尚不明确的现象和无关事项。直接依赖按实际链路核查，不能仅因位于公共模块就排除；新增写入范围仍遵循已有授权规则。

用户提供的页面或原型已足以支持任务时，旧参考目录缺失不作为任务阻塞。页面上的其他报错、历史问题或未到阶段的验收工作，也不能自动变成本次开发内容。仅有证据表明影响目标行为时再作最小范围排查；无关事项不混入方案问题清单，不借边界检查顺带修复。

## 唯一授权规则

所有角色及任务交接均使用以下判断，不另设权限解释：

### 方案文档交付与实施关口

本关口适用于本工作流中的正式业务开发；技能维护本身不启动业务工作流。按以下顺序执行，不能用聊天中的范围摘要或选择框替代完整方案文档：

1. **先完成并交付文档。** 将业务行为、完整必要契约、目标仓库与文件影响、实施清单、操作边界、风险、验证与完成条件，以及适用的收尾安排写入同一主方案，按“输出前检查”复读实际成品。在聊天中提供可点击且可访问的完整文档链接、当前版本标识及必要摘要，状态为“方案待确认及授权”。只有本地写入、工具输出路径、未交付的草稿或节选均不算交付。
2. **再取得针对文档的确认。** 在交付消息中明确询问是否确认该链接所指版本的完整方案并授权按清单实施。业务规则、字段或开发范围的选择（例如“采用此规则”“按建议开发可用部分”）只更新需求和范围，不能当作方案授权。尚未交付完整文档时，“可以”“继续”“直接做”等不能用于跳过本关口；不得把范围选择框包装成完整方案审批。文档已交付且紧邻事项唯一明确为该方案的实施授权时，可以接受简短肯定回复，不要求固定口令。
3. **核对证据后才启动开发。** 记录方案路径与已交付版本、交付消息及用户确认依据、获批范围；证据必须满足“文档交付在先、确认在后、开发最后”。缺任一项时，可继续只读核查、需求澄清及方案编写，不得创建开发 worktree、分派实现任务或写入业务代码。不能先宣布执行中、派发开发或写代码，再补文档、补授权记录。

已有满足上述条件的授权持续有效，不因阶段或角色切换重复确认；范围选择仍需合入主方案，新增范围按实际差异申请增量授权。若发现已越过关口，停止受影响开发，如实说明已写入内容，保留现有改动并补齐可审查文档后等待确认；不得追认旧的范围选择为方案批准，也不擅自回滚。

### 授权范围与延续

| 类别 | 处理 |
| --- | --- |
| 已有明确授权 | 核对范围及最新指令后直接执行，不因换阶段、角色、工具、会话或常规技术细节再询问 |
| 本流程默认包含的操作 | 纳入统一方案说明；方案获实施授权后连续执行，用户已有明确授权不重新取得 |
| 超出范围或存在实质歧义 | 先准备具体方案，集中申请增量授权；只暂停依赖该授权的工作 |

主技能已明确启用且方案获实施授权后，正式开发的默认操作包括：按 [分支与运行环境](coordination.md#分支与运行环境) 创建或复用独立任务 worktree、任务分支及必要的本地忽略配置，主目录开发仅适用有明确理由的例外；必要的本任务服务启动、重启与独立端口；浏览器验证；在已确认开发环境和获批操作范围内，通过正常业务流程产生可识别、可清理的必要验证数据（遵循 [缺数据先查业务链路](acceptance.md#缺数据先查业务链路)，不包含直接补造业务事实或历史回填）；已确认功能范围内的菜单；范围内修复复测；按约定条件仅提交任务增量、合回开发基线、推送到方案明确的远程目标分支，核验远程包含交付提交后清理任务资源。保护和执行条件见另两份公共规则。端口、目录等常规选择自行核实；本地端口冲突自动选择空闲端口并同步本任务连接配置，按 [执行协作](coordination.md#分支与运行环境) 继续启动和验证，不重复申请已有授权，不绕过审批拒绝。

统一方案须写明目标仓库、开发基线、远程目标分支及提交、合并、推送、远程核验和清理范围。**用户确认方案并授权实施后，即已授权该完整收尾链；人工验收通过后自动连续执行，不在合并、推送或清理阶段逐项再次询问。** 仅新增范围、目标发生实质变化或用户另设限制时，按实际差异处理增量授权；单纯进入推送阶段不构成新授权事项。

正式业务开发的方案应明确**先人工验收，再合并或回写**，仅用户明确免除时可跳过；实施授权不等于人工验收通过，具体执行 [人工验收规则](acceptance.md#工程完成与人工验收)。此关口同样约束已授权的整合操作，不以方案中写有“自测后回写”作为免除依据。

默认范围不包含部署到共享测试或生产环境、数据库结构变更、修改原有业务数据、实际发布/审批及未授权外部效果、扩大角色权限或覆盖其他工作。这些若已获具体授权同样直接执行；否则只申请实际需要的增量，不重复申请整个任务。项目强制操作限制和用户明确保留的确认点仍有效。

数据库变更 SQL 是用户保留的手动执行关口：整体方案授权不授权代理执行 SQL；按 [数据库环境](coordination.md#数据库环境) 交付完整脚本并弹框确认用户已执行完成后，再推进依赖步骤。不将“批准方案”“允许执行”解释为用户已完成执行。

一次展示可预见完整操作链及边界后明确询问“是否确认方案并授权按清单实施？”。不能先单独确认接口再申请同一方案；也不能把初始开发目标、局部口径回答或只确认设计当作对完整实施清单的批准。“可以、继续”根据紧邻的唯一明确事项理解，有歧义才澄清。用户只批准子集时准确记录子集；后续撤回、暂停或范围调整优先。

新增授权申请写清目标环境、对象、完整操作步骤/命令或脚本、影响、验证及必要回退；长清单可链接完整文件，当前回复仍保留范围与关键影响。无法自行核实的必要信息集中询问，不编造环境或命令。已有成功操作不重做。

## 授权交接

主控向子代理或已获准联系的会话传递：已交付方案的路径与版本、交付及用户确认依据与原意、任务与仓库/环境、已批准操作和条件、尚缺授权及排除项，以及人工验收状态、适用版本/范围和用户明确通过或免除的依据；明确哪些直接继续。执行者须核对方案文档交付与实施关口，不能仅凭“用户已确认”或范围选择开始实现；证据缺失先向主控核实。不能只说“读最新 Skill”，也不能以“授权不明再申请”将已批准事项重新挂起。

修改通用 Skill 本身与批准具体任务不同；用户已明确批准用于当前任务时如实传递，不能降格为文档更新。接收方核对可信依据和适用范围后沿用；上下文缺失先查记录或请主控补充，不直接让用户重答。错误交接须在已有通信授权内明确更正，并同步撤销已解决的待确认状态。授权交接不自行赋予联系其他会话的权限。

## 精简记录与反馈

本节适用于所有过程文档及角色交接：需求、设计与实施方案、进度、审核、测试和交付记录。统一遵循“重点先行、更新增量、定义唯一”。当前主方案应能独立读懂；“增量”指更新时合并变化，不要求读者拼接历史消息才能理解本次方案。

任务进行期间，记录放用户指定位置、项目约定位置，或项目内 `.codex/workflows/<任务标识>/`；跨仓库维护一处主记录。收尾时按 [证据与备份清理](acceptance.md#证据与备份清理) 先归位必要长期资料，在任务目录外保存交付摘要，再删除满足条件的整个任务目录，不默认永久留存过程文档。简单任务一份文档即可容纳方案、授权、进度、证据和交付，不强制目录、表格或独立角色报告。复杂任务仅按阅读需要拆分；不为缩短正文把所有内容搬到另一份长文，也不批量改写或迁移已有业务文档。

- **开头直接给重点**：当前状态、本次变化、实际问题和待决策项；每项先用一句话给结论，再补必要依据。摘要以一屏可读为目标，不截断必要信息；没有的栏目省略，不填“无”凑结构。问题说明影响，待决策项说明需要选择什么，不把已获授权的执行事项列为待确认。
- **正文只写有用内容**：已确认且未变化的完整定义引用原位置，保留理解当前方案所需的简短结论；常规已核实事项一句话带过，无助于理解变化或判断结果的内容删除。保护代码、遵守规范、检查测试报告等通用流程留在 Skill，不逐任务复制。未知、失败、跳过及未验证项不能当作“常规无问题”省略。
- **必要定义只维护一次**：保留可实施的接口、字段、状态和业务规则、数据库改造及历史数据处理、必要新增/修改文件及作用。需求、契约、执行安排和验证证据各有明确位置（可为同一文档的不同节）。允许摘要用业务语言概括并链接完整定义；不重复维护整张字段表、文件清单、操作清单及授权范围。摘要与正文必须同步，摘要不得新增或改变约束。
- **执行细节按需查阅**：执行要求不等于逐项展示要求。worktree、代码保护和只读核查仍须执行，摘要只呈现本任务实际操作及风险，具体目录、端口和处理步骤归入执行详述。正文保留影响判断的操作范围、环境、风险、完成条件及验证结论。完整命令/脚本仅在具体授权或可复现执行需要时保留一次，并提供可点击入口；日志、哈希、进程信息等必要证据放记录的细节区或证据文件，不堆在审查摘要。精简不削减授权申请所需的完整范围和实际影响，敏感信息脱敏。
- **重点信息明确加粗**：本次变化名称、关键业务约束、主要风险与授权边界、需要用户回答的核心问题，用加粗短语或短结论突出；原因和实现说明用普通文字。一段通常只突出一个核心判断，不整段加粗、不把所有列表项全部加粗。状态及待决策标签仍独立成段；标题负责分层，加粗负责层内重点，不能代替内容整理。平行信息才用列表，需要对照才用表格；导航沿用真实原型名称与层级，审查分组不冒充菜单。
- **更新当前结论而非堆追加记录**：已解决问题移出当前待办，已批准事项移出待确认；保留必要的确认依据、版本和证据链接即可。已完成步骤不再写成“拟执行”，失效命令和旧授权请求不与当前安排并列。交付前检查状态、剩余项及人工验收/清理安排是否一致；本规则用于后续生成和任务内必要更新，不自动触发历史文档重写。

角色结果可直接交接，由主控更新同一记录。正式业务开发默认状态为需求待确认、方案待确认及授权、执行中、验证中、待人工验收、已交付；用户明确免除人工验收时记录依据并跳过该阶段，阻塞附在当前阶段，不为阶段名制造审批。聊天同样突出结果、变化、具体问题与下一步，详细定义链接正文。用户可直接回复或圈图，不要求填模板；不承诺 Markdown 自带批注。

### 生成与修订顺序

编写或更新方案时执行以下步骤，短任务可在几段内完成，不要求单独交付提纲或检查报告：

1. **先判断任务类型，再组织变化。** 核对最新状态、授权、已写入范围、有效验证和缺口。已有功能的补齐或修复，按“当前已有什么 → 已证实缺口 → 本次变化”组织，沿用规则集中说明；新增功能或复杂契约变化才展开必要业务全景，不把每个任务都写成从零设计。每项变化关联依据、目标结果和验收方式，区分已证实问题与建议防护，不能把未经核实的风险写成现有缺陷。开头呈现目标、状态、关键变化、主要影响及仍待决定的事项，没有的栏目省略；一个实质取舍一个短段，不把多个决定压成长段。
2. **先划分功能，再在各功能内先写业务、后写技术。** 按用户可识别、可分别验收的功能划分章节，不以仓库、前后端或角色划分功能。每个功能集中写用户操作、可见结果、适用条件、例外和失败反馈，再补该功能的接口、数据处理、修改范围、实施与验收。组件名、DTO、字段映射、行锁、事务和 DDL 放在所属功能的技术小节；理解业务不可缺少的术语用中文解释。真正共用的定义集中维护并链接引用，不能以简化为由丢失校验、权限、副作用或失败边界。
3. **重新读取实际成品并修订。** 首次写完、合并角色结果或更新任务阶段后，重新读取最终文件中受影响的章节及摘要、状态、待办和证据区；按下文检查发现问题并直接修正。只有实际完成这一步后才交付或请求实施确认，不用写入成功、章节存在、关键词命中或格式检查代替内容与可读性复核。

例如，业务层写“同一申请只允许处理一次，重复或过期操作提示刷新，失败不留下部分结果”；技术层再完整说明请求标识、状态核验、锁定范围和事务回滚。不能只是给原技术长段加一个业务标题。

### 阅读层次与版式

多功能方案以功能为正文主线，逐个讲完整，不先汇总所有功能的业务、再汇总所有接口和测试。默认仍维护一份完整方案，不要求每个功能拆成独立文件或单独授权。通常采用下面的阅读顺序，短任务合并成几段即可，不机械生成所有章节：

1. **决策摘要：这次做什么，需要关注什么。** 状态单独一行，接一句话业务目标、少量关键变化、主要影响与当前需要用户决定的事项。重要取舍和会阻塞实施的未知在此露出，不能埋在文末。仓库哈希、完整路径、命令和通用保护条款放细节区；不以缩小字体、超宽表格或堆分号达到“一屏”。
2. **功能逐项展开：每个功能在本章形成完整阅读路径。** 每个独立功能使用一个主题章节，依次说明目标与操作、业务规则与异常、接口及数据处理、修改范围、实施步骤与验收标准，然后再进入下一个功能。前后端内容归入同一功能；不因共用页面或 Service 就合并独立功能。各小节按实际需要保留，先用业务语言给出结果，再展开完整技术定义。计划验证与已执行结果分开，功能与视觉验证分别说明。
3. **公共安排：只集中真正共用的事项。** 环境、跨功能依赖和联调顺序、共同风险、整体授权及提交合并推送清理集中维护。共用接口、字段、规则和文件职责只定义一次，各功能链接到准确小节并说明与本功能的关系；同一文件承载多个功能时，分别说明各功能的改动职责，不重复整份文件清单。功能特有的接口、异常、测试与证据留在该功能章节，不能借公共章节重新混合。

结构示例（仅示意组织方式，不是完整方案）：`1. 审查摘要`、`2. 二维码贴妥后发货`、`3. 配送单详情`、`4. 公共安排`。第 2、3 章各自包含业务、技术、修改范围和实施验收；不能仅拆开业务小节，却仍将两个功能的全部接口和测试混放到文末。进度、审核和交付记录沿用相同功能名称归组，跨功能结论单列。

正文含多个详述章节时，在摘要后提供少量可点击阅读入口，而不是再造一张重复摘要。根据任务及项目模板调整章节名称和顺序，但必须保留以下编号要求及“先业务结论、后完整定义”的阅读路径；用户明确指定其他编号格式时遵循其要求。

- **长方案必须使用显式章节编号。** 涉及多个业务场景，并需要分别展开实施、验收及技术契约的方案，主题标题使用 `## 1. …`、`## 2. …`、`## 3. …`，独立场景小节使用 `### 2.1 …`、`### 2.2 …`。编号按层级连续，同一文档不混用有编号和无编号的同级正文标题；文档总标题不编号。短问答、局部小修复不强制套长方案结构。不能仅给目录或 Skill 内的说明列表编号，实际交付文件的标题也必须编号。
- 标题通常使用文档标题、主题、小节三级，表达具体问题或结论，如“2.1 联系人独立保存，不触发重审”，避免仅写“其他”“补充”或持续追加“本次新增”。每个业务小节开头先给业务结果，再分别说明条件、例外及失败反馈；新的需求归入对应主题。
- **步骤与审查事项逐项列出。** 实施顺序、验收步骤及需要用户逐项回应的事项使用有序列表 `1.`、`2.`、`3.`，不写成一串箭头、分号或逗号。普通并列属性仍可用无序列表；编号用于定位和核对，不能把一整段混杂内容放进一个编号项。
- 一段只解释一个中心结论。规则、依据、实现和风险若需要分别判断，就分段或设小节；不能只把长段改成长列表。不要按固定字数截断必要定义。
- 表格用于同维度对照，通常控制在 2–4 列。单元格开始容纳多个条件、例外和实现说明时，提取短结论，把完整解释放对应小节；接口总览只做索引，完整请求、响应、权限及错误约束按接口展开。
- 状态和实质待决策项使用独立标签与空行，重点按上文“重点信息明确加粗”处理，图标不铺满标题。例如写“已提交企业**至少保留一位联系人**”，不用整段粗体或只加粗“注意”而隐藏实际约束。
- 已确认规则、拟议设计、尚未核实事实分别标明。涉及批准的完整对象、操作及影响保留在可访问的正式方案中；结构示例或节选明确标注，不能冒充可授权实施方案。

### HTML 阅读版与结构化技术内容

正式方案维护一份 Markdown，生成同版本自包含 HTML；不手工维护两套正文。HTML 内嵌样式与交互，不依赖 CDN，不自动执行文档中的命令、请求或 SQL。版本、状态、风险和授权边界来自源文件；修改 Markdown 后重新生成并交付，不能沿用失效 HTML。生成器记录源文件 SHA-256，供一致性检查。

**阅读布局**：首屏给状态、目标、3～5项关键变化及待决定事项；随后按 Markdown 的功能章节顺序展示，每个功能先业务、后技术与实施验收，公共安排单列。目录应能直接定位各功能及其小节，不重新按业务、接口、测试跨功能归组。摘要与各功能的业务说明应能独立支持业务判断。宽屏侧边目录，窄屏顶部目录；正文限宽、留白、短段落，标题通常三级以内。长内容局部滚动，不让整页横向溢出。

**色彩语义**：目标和接口重点用浅蓝，待确认或风险用浅黄，技术和代码用浅灰，业务正文白底。颜色只辅助理解，必须同时有标题或文字标签。使用 Markdown 引用块承载提示卡片；待确认、风险等标签保持明确。不要把每段都做成卡片，不依赖折叠隐藏必要条件。

**接口格式**：每个接口以方法标签、完整路径和中文用途开头，再说明认证、调用条件及副作用；请求参数表列名称、类型、必填和约束。请求、成功响应分别使用带 `json` 语言标记的代码块；异常使用“触发条件／返回含义／调用端处理”的短表。表格不塞长段落。完整响应包装只有核实后才展示；仅展示 data 时明确标注，未知字段与错误码不编造。示例不能替代正式类型和约束。

**SQL 格式**：每份脚本明确用途、目标数据库、涉及对象、影响、前置条件及执行顺序；完整脚本使用 `sql` 代码块，再列验证语句、适用的回退办法。无法回退或涉及删除时明确提示。执行与验证状态分开；展示、复制、批准方案均不等于已执行。无 SQL 变更只用一句话说明，不生成空章节。用户手动执行关口保持不变。

**代码呈现**：JSON、SQL、命令使用等宽字体、保留缩进换行，提供语法高亮、局部横向滚动和复制按钮。不得截断或用省略号替代必要内容。复制失败显示提示，不能伪报成功。外部内容作为文本渲染，不执行原始 HTML。

复用 `assets/plan.html` 和 `scripts/render-plan.mjs`。生成器使用已有 Node.js 和 `marked`，优先通过宿主的 workspace dependencies 工具定位依赖；缺少运行时需如实说明，不向业务项目添加依赖。调用方式（将参数替换为实际完整路径）：

```text
node scripts/render-plan.mjs source.md output.html --modules /absolute/node_modules
```

输出前核对源文件版本、状态和哈希，检查宽屏与窄屏、目录跳转、代码完整性和复制行为。SQL 格式可用明确标为排版测试的临时样例验证，不往无 SQL 需求的正式方案添加假脚本。打印和禁用脚本时正文仍完整可读。交付 HTML 及源文件链接；宿主不支持 HTML 预览时，明确提供浏览器打开方式，不声称已经预览。

### 输出前检查

对实际成品执行以下检查；发现问题先修正文档，再交付或请求实施确认。先读取实际标题与开头摘要，再通读受影响正文；有 Markdown 预览能力时同时检查渲染结果，没有时检查源文档并如实限定验证范围。只检查本次新增或更新内容及其关联状态，不因此启动全量审核、新增代理或增加用户审批：

- **功能能逐项完整阅读。** 选取各独立功能，检查能否在所属章节读到业务行为、必要契约、修改范围与验收方式；除明确链接的共用定义外，不应需要从其他功能或全局接口、测试清单拼回该功能。共用内容只维护一次，跨功能依赖明确，HTML 与 Markdown 的功能分组一致。仅给混合内容加功能标题，不算完成重组。
- **编号能直接用于审查。** 核对长方案实际章节是否采用连续的 `1、2、3` 和 `2.1、2.2` 层级，独立功能是否有对应主题章节，实施及验收步骤是否逐项编号。调整编号后同步目录、锚点和交叉引用；只有目录带编号、正文仍为无编号长段，不算通过。
- **摘要能独立支持判断。** 仅读开头能否说清目标、当前状态、关键变化、需要决定的事项和主要缺口？若取舍首次出现在文末，提前给出业务结论；若多个取舍挤在一段，分别呈现，不重复整份设计。
- **变化与沿用规则可区分。** 已有功能是否一眼可见本次改动及依据，而无需读者自行从全量规则中比较？建议防护是否被误写成已发生缺陷？已有可靠定义引用原位置，保留理解本次变化必需的结论；没有可靠引用时仍保留完整定义。
- **每段有明确用途。** 是否帮助理解变化、作出决定、实施或验收？无作用的过程描述删除，必要工程细节归入对应详述；不影响当前判断的旧路径缺失、无关报错和不适用检查项不逐条陈列。未知、失败及验证缺口若影响当前结论必须保留，不能以精简为由掩盖。
- **重点能直接定位。** 只读摘要、标题及加粗短语，能否找到本次变化、关键约束、主要风险与授权边界、待回答问题？再对照完整正文，关键项不能只埋在普通长段或表格里。将遗漏重点提前概括，在相关业务小节加粗核心约束；避免满篇粗体，加粗不能改变事实状态或代替拆分混杂主题。仅统计粗体数量或确认关键词存在，不算通过。
- **业务层不要求读者理解代码。** 暂时跳过技术详述，仅阅读业务部分，能否说清每个场景的用户操作、可见结果、适用条件、例外和失败反馈？若必须理解字段名、DTO、锁、事务或哈希算法才能判断，先改写成中文业务规则，再将实现机制移到对应技术小节；完整契约仍须保留并可定位。不能只增加“业务行为”标题而保留原技术长段。
- **每段和每格只承担一个判断主题。** 若混合多个独立规则、取舍、实现或证据，按主题拆成小节、短段或简短对照；不能把长段原样变成长列表，也不按固定字数切碎连贯说明。接口、文件和验证项按主题组织，避免一条清单承载多个检查维度。
- **正文与摘要没有丢失或改变定义。** 对照原始要求或修改前内容，核对必要契约、校验、权限、失败边界和授权对象仍有唯一完整位置，链接可达；已确认、拟议和未核实内容不混写。示例不能变成所有任务的强制模板。
- **当前状态在全文一致。** 依据最新有效指令和执行证据，同步摘要、阶段、执行清单、授权及验证记录；开始后不仍写“尚未写入”，暂停后不仍标“实施中”。历史事实需标明时间或历史属性，计划步骤与已执行结果分开。没有新证据不能把“未验证”改为“通过”，用户暂停也不能被文档整理解释为恢复授权。
