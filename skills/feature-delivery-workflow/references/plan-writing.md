# 方案编写与阅读版

### 生成与修订顺序

1. 核对当前状态、授权、已写入范围、有效证据和缺口。已有功能按“现状 → 已证实缺口 → 本次变化”组织；新增或复杂契约才展开必要全景。变化关联依据、目标和验收，推测风险不能写成已发生缺陷。
2. 按页面分章、页面内按功能展开，先业务后技术；完整结构见下节。先讲数据处理或操作逻辑、结果、条件与失败，再写页面与组件、对应接口、文件、实施及验收，不能只给技术长段加业务标题。
3. 首次正式交付前通读完整成品，核对完整性、授权范围和可读性。后续只读变更章节及实际关联的摘要、状态、待办、证据和引用；阶段或角色切换不触发全文复读。重新交付前核对版本与整体状态一致性，有矛盾再定向扩查。发现问题先修正，不能用写入成功、关键词或格式检查代替内容复核。

### 按页面组织，页面内说明逻辑与接口

先列页面总览：页面名称、用途、新增或修改、入口与跳转关系。按实际产品视图划分列表页、独立详情页、新增页和编辑页，每个页面独立成章；页签、弹窗、抽屉作为所属页面的子视图，复杂或跨页面复用时单独展开并标明入口。只有一个页面时不人为拆页，无页面的后台任务按业务能力组织。

页面内按功能说明“数据处理或操作逻辑 → 布局与组件 → 接口设计 → 实施与验收”。查询与增删改分别说明逻辑，共用定义只写一次；同页多个独立操作用小节或短条目保留边界，不提升为与页面并列的章节。

- **查询逻辑**：用几句话说明数据来自哪个业务对象及已核实的表、服务或上游接口，怎样筛选、关联或汇总并返回。按需补充上游产生入口、纳入/排除条件、分页排序与后续去向，区分后台查询和前端展示处理。不能只写“调用查询接口”，简单查询不展开完整 SQL 或调用栈。
- **复杂字段来源**：在页面设计前说明字段含义、来源对象/字段、关联及计算或取值规则，必要时说明缺失值处理；区分快照、实时值和汇总值。普通直接映射字段不逐项展开，来源未核实则标明缺口，不用近义字段或固定值冒充。
- **新增、编辑、删除逻辑**：说明操作权限与条件、关键校验、写入或删除的数据、状态变化、关联影响及失败结果。新增说明默认值和关联来源，编辑说明回填及可改范围，删除说明物理/逻辑删除与关联数据处理。保存、提交和审批生效分别说明；并发、事务等只在相关时展开。
- **页面与组件**：说明页面、表单、弹窗或抽屉的主要布局、关键交互、回填刷新及成功/失败反馈；列出项目组件名称、用途及复用或新增封装。依据已确认原型和项目约定，不只写“沿用项目风格”，也不罗列全部基础控件。
- **接口设计**：将页面操作对应到接口，说明方法、路径、用途和调用时机，明确标记“新增／复用原有／修改已有”。新增说明现有能力缺口，修改说明契约差异与兼容影响，需要扩展字段或行为的接口不能标为纯复用。按下文格式展开必要契约；未变契约引用已核实定义，未知接口或组件标为拟议或待核实。

  在线接口文档不可用时，按 [接口契约核验与依赖](coordination.md#接口契约核验与依赖) 判断能否以对应版本源码完成方案核对。标注现行契约的证据来源及版本，区分源码已核实、方案拟新增或变更、目标环境待验证。仍有证据缺口时，写明缺项及其影响的具体步骤，继续交付可独立核实的内容。

最后说明修改范围、实施步骤与验证方式。涉及页面时，列明受影响页面及子视图的实际视觉检查和代表性内容，按 [页面与子视图实际视觉验收](acceptance.md#页面与子视图实际视觉验收) 分别安排逻辑测试、真实流程与视觉检查，不用测试通过代替页面检查。短功能几段讲清即可，不强制表格，不重复字段和契约，也不另交提纲或自检报告。

### 正文简洁与细节归位

页面业务正文用独立小标题或独立标签分出以下三块，按实际内容保留，不用“查询、保存与提交”一个标题包住连续长段。页面内多个子视图或功能可分别组织，共用规则引用唯一位置。

- **数据来源**：优先用“数据／来源与取值方式”短表，少量内容用短条目。明确从哪里取、纳入哪些记录、如何关联或汇总；复杂字段写明实时值、快照或计算口径。不能仅列接口名称或业务对象而不解释取数方式。
- **处理流程**：有连续流程时先给一行简短步骤链，再用编号步骤说明“触发操作 → 系统处理 → 结果或下一状态”；查询则说明筛选、组装、返回。关键分支紧邻对应步骤，不把并列操作伪装成必须顺序执行的流程。每步先写中文动作或结论，一个条目只讲一件事。
- **重点限制**：用“简短标签：规则及影响”的短条目突出权限、可编辑条件、冻结范围、失败或阻断结果等关键边界。只列影响业务判断的限制，不把全部参数校验搬来，也不重复流程正文。

三块内容须能直接扫读；不能只增加标题、加粗或将原长段搬进列表和表格。来源表不塞事务细节，流程步骤不混入字段类型、锁顺序或存储设计；必要技术细节移至以下对应章节，保留完整定义和定位引用。

- 查询正文保留数据来源、筛选和组装方式；复杂字段保留业务含义与取值口径。准确表名或字段名仅在帮助定位来源时出现，详细映射放接口或数据设计。
- 操作正文保留用户能做什么、限制和可见结果。例如“记录已变化时拒绝覆盖并保留输入”；修订参数、锁与事务实现放对应技术章节。
- 页面组件优先用“区域／组件与用途”短表呈现，少量组件可用短条目；回填、刷新和失败反馈另用短句说明，不混入接口参数。
- 参数类型、权限编码、枚举、空数组与 null 语义归接口约束；表字段、附件关联和迁移归数据设计；校验职责、事务、锁和幂等机制归实施说明。留在所属页面或公共设计内，已有对应位置直接复用，不机械增设章节。

必要细节只在对应章节完整定义一次，其他位置按需引用。不得以简洁为由删除业务限制、失败结果或待决策事项，也不靠缩小字体或折叠隐藏必要内容。

### 数据库变更及原因

正式方案固定保留“数据库变更及原因”章节，并在目录中提供入口；即使无变更也明确写出结论和原因。统一汇总表结构、菜单/权限/字典等配置数据、历史数据迁移，不把“无表结构变更”等同于“无数据库变更”。共用变更集中说明，各页面引用，不重复脚本。

优先用“类别／本次变更／原因”短表说明。存在变更时，补充目标库表、具体改动、影响、执行与验证方式，必要时说明恢复办法；字段与脚本细节归对应技术位置。无变更时说明复用现有能力的依据；依据未核实则标为待核实，不能断言无需变更。菜单变更须说明缺少或调整入口的原因，无变更不生成空 SQL 或虚构迁移。方案交付时展示数据库模式选项、目标和影响，说明实施已授权后等待 60 秒未选择即采用沙盒自动执行；已有明确选择沿用。具体规则引用 [数据库环境](database.md#数据库环境)，不把模式选择或超时当成实施授权。

### 阅读层次与版式

维护一份完整方案，按页面逐项讲完整，不按仓库、前后端或角色分章，不因分章增加授权。短任务可合并段落；复杂方案按以下顺序：

1. 决策摘要：独立状态标签、一句话业务目标、关键变化、影响及待决定事项，重要取舍和阻塞未知在此露出。路径、哈希、命令及通用保护细节不占摘要；不靠小字体、宽表格或分号压成“一屏”。
2. 页面总览：列明实际页面及子视图、用途、变更类型、入口与跳转关系，便于核对多页面范围。
3. 逐页设计：每个页面独立成章，页面内按功能展开逻辑与复杂字段来源、布局组件、接口、实施验证。页面特有规则、异常和证据留在本章；技术细节归对应位置，业务说明可独立阅读。
4. 公共设计：跨页面共用的规则、组件、接口只定义一次，各页面保留自身调用映射并准确引用。同一文件跨页面时分别说明职责，不复制整份清单。
5. 数据库变更及原因：固定章节和目录入口，按上述规则汇总，页面引用对应变更。
6. 整体实施与验收：集中说明跨页面依赖、联调顺序、环境、共同风险、授权与收尾范围。进度、审核和交付沿用页面名称，页面内分别核对相关功能，跨页面结论单列。

版式约束：

- 多场景且分别展开契约、实施和验收的长方案，实际主题标题连续编号 `## 1. …`、`## 2. …`，场景小节用 `### 2.1 …`；同级不混用编号，总标题不编号。用户指定其他格式时遵循用户。短问答或小修复不强制长方案结构。
- 标题通常三级，表达具体问题或结论；新需求归所属主题，不堆“其他/补充/本次新增”。多个详述章节在摘要后给少量定位链接，不另造重复摘要。编号改变同步目录、锚点和交叉引用。
- 实施顺序、验收步骤和待逐项回应事项使用有序列表，每项一个判断主题；普通属性可用无序列表。段落不混塞规则、依据、实现和风险，也不按固定字数拆碎必要定义。
- 表格通常 2–4 列，仅对比同维度信息，长条件、例外和实现说明移至对应正文。接口总览只作索引，完整请求、响应、权限、错误按接口展开。
- 状态和待决策标签独立成段，核心约束简短加粗，不整段粗体。已确认、拟议、未核实分别标明；计划验证与实际结果、功能与视觉结论分别说明。示例/节选明确标注，不能冒充完整可授权方案。

### HTML 阅读版与结构化技术内容

正式方案维护一份 Markdown，生成同版本自包含 HTML；不手工维护两套正文。HTML 内嵌样式与交互，不依赖 CDN，不自动执行文档中的命令、请求或 SQL。版本、状态、风险和授权边界来自源文件；修改 Markdown 后将旧 HTML 标记为待更新；下次交付或供用户阅读前重新生成同版本 HTML，不交付失效版本。批量内部编辑结束后生成一次，无需每次状态写入都渲染。生成器记录源文件 SHA-256，供一致性检查。

**阅读布局**：首屏给状态、目标、3～5项关键变化及待决定事项；随后展示页面总览和逐页设计，页面内先展示可扫读的“数据来源、处理流程、重点限制”，再展示组件、接口与实施验收，公共设计及整体安排单列。目录应能直接定位页面、子视图和数据库变更章节，不重新按查询、增删改或接口跨页面归组。摘要与各页面的业务说明应能独立支持业务判断。宽屏侧边目录，窄屏顶部目录；正文限宽、留白、短段落，标题通常三级以内。长内容局部滚动，不让整页横向溢出。

**色彩语义**：目标和接口重点用浅蓝，待确认或风险用浅黄，技术和代码用浅灰，业务正文白底。颜色只辅助理解，必须同时有标题或文字标签。使用 Markdown 引用块承载提示卡片；待确认、风险等标签保持明确。不要把每段都做成卡片，不依赖折叠隐藏必要条件。

**接口格式**：每个接口以方法标签、完整路径和中文用途开头，再说明认证、调用条件及副作用；请求参数表列名称、类型、必填和约束。请求、成功响应分别使用带 `json` 语言标记的代码块；异常使用“触发条件／返回含义／调用端处理”的短表。表格不塞长段落。完整响应包装只有核实后才展示；仅展示 data 时明确标注，未知字段与错误码不编造。示例不能替代正式类型和约束。

**SQL 格式**：每份脚本明确用途、目标数据库、涉及对象、影响、前置条件及执行顺序；完整脚本使用 `sql` 代码块，再列验证语句、适用的回退办法。无法回退或涉及删除时明确提示。执行与验证状态分开；展示、复制、批准方案均不等于已执行。无 SQL 变更时仍保留“数据库变更及原因”章节及目录入口，简述无变更及依据，不生成空脚本。执行方式遵循 [数据库环境](database.md#数据库环境) 的当前任务模式；自动执行与手动执行完成确认分别处理。

**代码呈现**：JSON、SQL、命令使用等宽字体、保留缩进换行，提供语法高亮、局部横向滚动和复制按钮。不得截断或用省略号替代必要内容。复制失败显示提示，不能伪报成功。外部内容作为文本渲染，不执行原始 HTML。

复用 `assets/plan.html` 和 `scripts/render-plan.mjs`。生成器使用已有 Node.js 和 `marked`，优先通过宿主的 workspace dependencies 工具定位依赖；缺少运行时需如实说明，不向业务项目添加依赖。调用方式（将参数替换为实际完整路径）：

```text
node scripts/render-plan.mjs source.md output.html --modules /absolute/node_modules
```

每次正式交付核对源文件版本、状态、哈希及新增/修改内容的完整性。首次交付检查实际内容在宽窄屏的布局、目录定位和代码显示；后续仅检查受内容变化影响的布局、锚点、代码及相关链接。

复制、打印、禁用脚本等模板能力，已有同模板、生成器、依赖和浏览器环境的有效证据时直接复用；任一相关条件变化、出现异常或缺少证据时补验对应能力，不因每次文本更新重跑模板测试。打印和禁用脚本时正文仍须完整可读。SQL 排版可用明确标为排版测试的临时样例验证，不往正式方案添加假脚本。按 [本地预览地址与审阅交付](#本地预览地址与审阅交付) 提供已验证的 HTTP 入口及源文件链接；预览不足时明确交付缺口，不声称已预览。

### 本地预览地址与审阅交付

生成 HTML 后，启动或复用本任务的本地静态预览服务。此操作属于方案交付，无需等待业务实施授权；只提供文档访问，不启动业务开发或执行文档中的操作。仅监听回环地址，仅服务方案及必要资源所在目录，不将整个仓库、用户目录或凭据目录暴露为静态目录。优先复用可核实的现有服务；端口冲突时选择空闲端口，不停止无关服务。

- **交付可用地址**：在聊天中优先提供完整、可点击的本地 HTTP 地址，使用实际主机、端口和文档路径；HTML 文件及 Markdown 源文件链接作为补充。不能只提供本地文件路径、`file://` 链接、启动命令或尚未启动的地址。
- **验证实际页面**：交付前在用户可访问的浏览器中实际打开该地址，核对完整内容、版本及源文件哈希对应关系；仅进程存在或 HTTP 成功不代表页面已验证。浏览器操作按 [验收浏览器](coordination.md#验证与验收浏览器) 执行。远程执行环境的回环地址不能冒充用户本机地址；用户端不可访问时如实列明预览缺口。
- **更新同一入口**：修订后重新生成 HTML，优先保持原地址与稳定锚点；刷新核对最新内容，排除旧缓存。地址必须变化时明确告知新入口及旧入口状态，不声称原批注会自动迁移。
- **保留审阅服务**：等待审阅期间保留服务，不因回复结束而关闭。在同一任务记录中简记服务目录、地址、进程及准确恢复命令；中断后在原范围恢复并重新验证，不承诺服务永久运行。Windows 后台启动使用隐藏窗口；收尾仅清理本任务服务，不影响其他任务。
- **分别报告批注状态**：本地 HTTP 地址是预览入口，不等于批注功能已验证。实际检查宿主批注能力后才能报告其可用；未检查则明确“页面访问已验证，批注功能未验证”。不擅自开发批注系统或写入测试批注。

本地服务无法启动、用户端无法访问或页面未能实际核验时，标为“预览交付未完成”，说明具体原因、已完成文档与待补项；不能仅凭 HTML 已生成宣称完整交付，也不能以文件链接替代后继续请求完整方案实施确认。用户明确接受其他交付方式时按其要求执行并记录边界。

### 输出前检查

按本文件“生成与修订顺序”确定检查范围。首次交付检查全部，后续仅检查受影响内容和关联状态；须核对本地 HTTP 入口及实际渲染；能力不足时继续源文档检查，但预览交付保持未完成。不因此新增代理、全量审核或审批。

1. **完整性与事实**：对照原始要求及修改前内容，必要契约、校验、权限、副作用、失败边界、授权对象仍有唯一完整位置且引用可达。事实、建议、未知不混写；涉及数据来源时，核对上述业务来源说明是否完整、与实际生产和消费链路一致，不能仅以字段映射齐全判定通过。未知、失败和验证缺口如实保留，示例不变成通用强制模板。
2. **阅读路径**：页面总览覆盖全部实际页面及子视图，入口与跳转清楚；每个页面内按逻辑、布局组件、接口、实施验收的顺序展开功能，共用定义有准确链接。查询能回答从哪里取、怎么查和怎么组装；复杂字段能追到来源；增删改能说明数据与状态影响；页面组件有名称和用途；接口有操作映射及新增、复用或修改已有的明确分类。跳过技术层仍能理解操作、结果、条件、例外和失败；HTML 与 Markdown 分组一致，不能只改标题而保留跨页面混排。
3. **审查定位**：摘要独立说明目标、状态、变化、决定和主要缺口；重点不埋文末或长表。长方案实际章节编号连续、步骤逐项，目录及引用同步；“数据库变更及原因”章节与目录入口齐备，表结构、配置数据和历史迁移的变更或无变更结论及原因明确。摘要、标题和加粗能定位核心约束，但不能仅统计关键词或粗体数量判为通过。
4. **表达必要性**：每段帮助理解、决定、实施或验收；每段/表格单元格一个判断主题。删除无关历史报错、不适用项和过程赘述，必要细节归位；不能把长段换成长列表或靠截断精简。逐页核对：读者无需从长段落提炼，就能在“数据来源、处理流程、重点限制”中定位来源与取数方式、处理步骤和结果、关键边界；不能只用标题存在作为通过依据。参数、表字段及事务等细节已归对应章节，组件说明可直接对照，不再混排成长段。
5. **状态一致性**：摘要、正文、授权、执行清单及证据符合最新指令和实际结果，区分计划、当前事实和历史。已开始不写未写入，已暂停不标实施中；无新证据不把未验证改为通过，文档整理不恢复已暂停授权。

修订后复读受影响部分直到具体问题消除，不能以“已复读”代替修正。必要事实仍缺失时说明缺口，不宣称满足完整审查。交付只报告检查范围与剩余限制，不输出自检流水账。
