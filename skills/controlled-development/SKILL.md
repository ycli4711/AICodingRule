# 可审查的业务开发

## 目的与边界

让用户在实施前看懂目标行为、关键契约、影响和风险，在交付时核对计划与实际。遵循当前指令、项目约定、已确认业务规则和已有授权；本 skill 不扩大操作权限，也不重复索取授权。

文案、注释、局部样式及行为明确的小修复可简述目标、影响和验证。复杂状态、副作用、契约或数据变化按实际场景展开，不机械填满所有栏目。事实、推断、建议和待确认口径分别标明；不要把示例当作项目契约。

## 场景路由

先确定主场景，再读取相关参考；一个任务跨场景时在同一份方案中组合，不拆成互不关联的方案，也不加载无关参考。

| 主场景 | 何时读取 |
|---|---|
| [接口开发](references/interface-development.md) | 新增接口，或改变现有接口的 URL/方法、请求与响应契约、校验、错误结果或权限 |
| [业务规则与状态流程](references/business-state.md) | 规则、合法状态转换或多步骤业务流程变化 |
| [业务 Bug](references/business-bug.md) | 现有行为与已确认规则不一致 |
| [数据库结构与数据](references/database-change.md) | 建表、改表/索引、预置或批量修改数据、历史数据迁移 |
| [外部集成与异步任务](references/integration-async.md) | 外部服务、消息、定时任务或异步副作用 |
| [性能优化](references/performance.md) | 以耗时、吞吐或资源使用改善为目标 |
| [代码重构](references/refactoring.md) | 以保持业务行为和对外契约为前提调整代码结构 |
| [页面与交互](references/ui-interaction.md) | 页面结构、用户操作、状态反馈或视觉实现 |

已有接口仅改变内部判断、查询、现有字段的默认值或业务结果，且 URL/方法、请求与响应结构、校验、错误结果及权限不变时，按业务规则、Bug、异步或性能等实际主场景写方案；接口只作为受影响入口，简述可见结果差异与契约不变的依据，不套用逐接口完整契约表和时序图。用户说“优化”也不自动归入性能场景，须以耗时、吞吐或资源改善为目标。涉及数据库查询或写入时，按风险另读 [SQL 与性能检查](references/sql-review.md)；不把普通接口单行插入机械套入数据迁移场景。工程配置、依赖、发布和数据迁移执行不设独立场景；若属于当前任务的必要部分，在对应方案中说明其影响、执行边界和验证。

## 实施前说明与授权

先只读核查实际代码、调用方、数据结构及已知旁路，按证据确定影响范围。涉及业务行为的任务，在第一次业务写操作前向用户实际发出与风险相称的执行说明：局部修复可简述，复杂任务给可审查方案。代码修改、测试数据写入和真实数据写入都受此顺序约束。只读核查后尚未实施，不称为“部分完成”。

读取 [方案展示与交付](references/proposal-template.md)，以业务目标开头，随后给所选场景的关键产物，再给实施步骤、影响范围、风险点、疑问和验证。影响范围必须判断；风险与疑问必须评估，不能为填栏目编造内容。复杂方案按用户级 AGENTS.md 的标题和独立标签格式展示，避免把不同内容压进长段。简单修复只用必要内容。

新增接口或改变对外契约时，按接口独立成节，分别列 URL、请求方式、适用的请求/响应字段、权限与错误结果，并各给一张时序图；总览表只能作索引，不能把多个接口的参数或流程合并成一份。请求方式只藏在正文、入参只写 DTO/包装类名、出参只写泛型返回类型，或把响应字段用顿号挤成一行，都不算已定义契约。缺少关键契约时，先补齐或标明待定及影响，不能请求该范围实施确认。复杂判断补核心伪代码，数据库访问补适用的参数化伪 SQL、影响行数与索引依据；图后的独立规则用编号列表表达。

页面开发与联调先核查任务范围内的页面模块、关键交互和可见状态，再逐模块对应接口及页面实际使用或保存时必须保留的字段；未看过的交互或未核实的字段不能写成已确认方案。只消费现有接口且不改变其契约时，引用已有文档或封装，不重写全部接口契约、未使用字段或逐接口时序图。其他场景按其参考展示最小核心表或清单，并在请求实施确认前核对完整性；不强制使用接口时序图，也不把多个规则、数据操作或指标挤成一段。

建表、改表、索引、预置或批量插入/修改数据必须在方案中单列结构或数据变化，说明目标环境、前后差异或来源与目标、预计影响、重复执行、兼容顺序及恢复依据。区分编写 SQL 文件、隔离验证和真实库执行；前两者不自动授权后者。普通接口按请求单行插入按实际风险简述。

影响正确性、授权范围或重要副作用的缺口，在相关操作前澄清；其他已授权且无依赖的工作继续。业务口径问题与实施授权分开。新功能、接口或数据契约、跨模块/跨仓库或高风险改造须在本轮具体方案展示后等待用户明确确认，再开始第一次写入；初始“请开发”不是该方案的确认。会话中此前已确认同一具体方案时不重复索取。没有确认消息就停在方案阶段，不能在同一轮方案后接着修改代码、测试数据或真实数据。

## 实施与交付

- 按方案实施，记录计划行为、实际行为、验证证据和有业务含义的差异。发现必要但仍属已授权范围的改动，说明影响后继续；新增业务规则、真实数据操作或未授权副作用按现有授权规则处理。
- 测试前核查数据连接和外部调用隔离；“运行验证”不等于授权执行真实支付、发信、批量任务或目标库写入。
- 按受影响入口验证成功、失败和关键边界；重试、幂等、并发及视觉对照只在相关场景或风险存在时覆盖。数据库查询按 SQL 参考核对实际查询和可用的执行计划证据。
- 交付时说明实际行为、文件与数据变化、验证范围、计划差异、剩余风险和未完成事项。只对有证据的结果标成功，不把编译、模拟测试或伪 SQL 当成真实环境验收。

需要理解流程示例时，读取 [冻结用户示例](references/freeze-user-example.md)；其中的状态、表名和权限均为教学假设。
