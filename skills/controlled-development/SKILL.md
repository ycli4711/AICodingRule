# 可审查的业务开发

## 目标与边界

让用户在实施前看懂业务行为，在实施中了解实质变化，在交付时核对计划与实际。提供结论、证据和取舍，不输出内部思维链。不用“优化、同步、修复、自动重试”等笼统词代替具体行为。

遵循当前指令、项目 AGENTS.md、已确认业务规则与授权；此 skill 不扩大权限，也不重复索取已有授权。开发接口、用隔离数据测试、调用接口操作真实数据、部署分别标注；前一项不自动授权后一项。此 skill 是工作方法，不是工具权限拦截器。

## 1. 只读定位并确定深度

- 核查实际代码、契约、表结构、索引和既有改动；区分已确认事实、合理假设及必要信息缺口。用户给出的文件是线索，不自动等于全部影响范围。
- 文案、注释、局部样式且无业务或数据行为变化：说明修改点，执行局部检查，不强行生成完整模板。
- 涉及业务状态、接口、权限、数据库或外部副作用：执行以下完整流程。小范围 Bug 可压缩篇幅，但保留实际涉及的状态、数据和副作用说明。
- 使用简短清单持续跟踪原任务与补充事项的口径、授权和完成状态。已授权且不依赖待答问题的事项继续推进。

## 2. 在第一次业务写操作前提供执行说明

读取 [方案模板](references/proposal-template.md)，按实际任务填充，省略无关项。先用业务语言说明，再补技术细节：

1. 目标、完成标准、必须成立的业务规则，以及尚未确认的关键选择。
2. 编号步骤与依赖：先查什么、再改什么、最后验证什么；标记只读、改代码、测试数据写入、真实数据写入或外部调用。
3. 伪代码：入口、判断、状态变化、事务、失败和重试路径。说明请求接受、业务完成、状态持久化和外部生效的区别。
4. 涉及数据库访问时，读取 [SQL 与性能检查](references/sql-review.md)，给出伪 SQL、预期影响行数、索引依据和未验证假设。未取得结构证据时标注示意，不把猜测字段变成既定契约。
5. 影响的模块及关键文件、缓存和等价入口；明确本次实际执行环境和验证边界。

技术实现可在已有授权内自行选择，但会影响用户可见行为的数据覆盖、状态先后、重试、补偿和缓存一致性等选择必须在执行说明中明确。若需要用户决定，集中问必要问题，不能把自己的默认建议写成已确认规则。

若现有授权已覆盖这份具体方案，告知后继续；若按当前指令需要确认，先完成只读核查和具体方案，再仅请求尚未授权的完整范围。用户确认绑定到该范围，不视为任意后续扩展授权。

## 3. 按说明实施并公开实质差异

- 维护一个精简的行为清单：计划行为、实际行为、验证证据、差异。清单可随任务更新，不必机械生成额外文件。
- 新发现的必要文件改动若仍在已授权业务范围内，说明影响后继续。新增业务规则、真实数据操作、跨仓库写入或其他未授权副作用，先描述新增差异并按现有授权规则处理。
- 不把“运行验证”当成调用真实支付、退款、冻结、发信或批量任务的许可。运行测试前核查数据连接、外部请求替身和测试隔离；条件不明时先澄清或改用安全的静态检查。
- 进度消息报告已确认行为、实质变化及下一步，不用事后通知替代事前所需的授权。
- 实际 SQL、ORM 生成查询、状态更新顺序与已披露方案保持一致；偏差有业务含义时说明，不能只报告文件数量。

## 4. 验证与交付

- 按受影响业务入口验证成功、失败和关键边界；有重试、并发或幂等行为时验证相应结果。测试强度与风险匹配。
- 核对实际数据变化、外部调用及旁路；数据库任务按 SQL 参考完成相应检查，不能以伪 SQL 或单元测试通过代替性能证据。
- 交付：完成的业务行为、实际文件变更、实际数据/外部操作范围、计划差异、验证证据和未完成事项。只对已核验结果标成功，区分模拟测试与真实环境验证。
- 用户指出规则遗漏时，围绕具体失误优化此流程；不自动把单个案例的业务规则升级成所有项目的通用要求。

需要解释流程或练习对齐时，读取 [冻结用户示例](references/freeze-user-example.md)。该示例是教学假设，不是项目契约。
