# 接口开发方案

适用于新增接口，或修改现有接口的 URL/方法、请求或响应字段与结构、校验、错误结果、鉴权或数据权限。先核对原型、调用方、项目路由和响应包装约定；尚无证据的字段或规则标为待定，不把建议写成已确认契约。现有接口仅改变内部实现或已有字段的业务取值、默认值而不改变上述契约时，按实际业务场景展示差异，不套用本文件的全量逐接口格式。

## 接口契约

- 逐个列出接口的 URL、请求方式、用途、调用方、鉴权/数据权限和与现有接口的关系。多个接口可先用总表作索引，随后每个接口单独成节；总表不能代替各自的契约和流程。
- 对新增接口列出请求字段及响应字段的名称、类型、必填性、默认值、枚举/取值约束和含义；说明分页、排序、ID、日期和响应包装。现有接口发生契约变更时逐接口突出变更前后差异、旧调用方兼容方式和错误结果；未变化的字段或共享 DTO 可引用现有契约，不重复整表。
- 明确成功、参数错误、无权限、对象不存在、状态冲突等实际适用的响应；错误码与消息遵循项目约定，不凭空定义。

新增或改变契约的接口在实施前方案中逐节展示（如“接口 1：新增”“接口 2：编辑”）；每节按下列顺序给出，现有接口只列变更字段及其兼容性，不用一段概述代替需要定义的字段：

1. 接口标识：`URL | 请求方式 | 用途 | 调用方 | 权限`。页面 URL 与服务端 API URL 分别写，不能互相代替。
2. 本接口请求字段表：`位置/层级 | 字段 | 类型 | 必填/默认 | 规则与含义`；说明 query、path、body 的实际位置。使用 `PageParams` 等通用包装时，核实并列出外层分页字段和内层业务筛选字段；给出符合项目结构的请求示例（路径、查询参数或 JSON body），不能只写类名。
3. 本接口响应字段表：`字段路径 | 类型 | 可空/取值 | 含义/来源`；每个实际返回字段单独一行，用 `data.records[].字段` 等路径区分包装、分页元数据和列表行。共用包装或未变化的共用 DTO 可引用已核实的完整定义，但须说明本接口实际返回内容及差异；本接口新增或供页面使用的字段须逐项列明，不能用顿号串联字段名或只写泛型返回类型。
4. 本接口实际适用的错误结果、兼容方式及待定字段。未确认项标“待定”及影响，不留空让读者猜测。
5. 本接口的核心逻辑：简单顺序用几句话或短步骤说明；关键顺序难以用文字说清时才给 Mermaid 时序图；复杂判断或数据访问再按需补伪代码或伪 SQL。说明和图都放在所属接口节内。

发出实施确认前逐个接口核对：URL 和请求方式是否明确；本接口请求字段与示例能否说明客户端实际怎样传值；响应字段能否让页面使用的每个字段查到类型、可空性和来源；本接口流程与错误结果是否说清。缺任一项时补全；确实无法核实时列出具体待定点与所需证据，先澄清受影响契约，不以“按现有约定”代替字段定义。只确认已完整列明的接口范围，不用一个笼统确认覆盖其他未核实接口。

## 业务流程

- 单个接口只有常规校验、查字典或数据、单次写入与返回，且几句话能说清顺序及失败结果时，用短段或步骤说明，不画时序图；不为简单 CRUD 编造分支、伪代码或外部调用。
- 跨系统、异步、复杂分支、事务与外部副作用的先后顺序影响结果，且文字难以清楚表达时，才为相关接口分别画 Mermaid 时序图。图只展示实际参与者及关键校验、状态改变、提交、失败和副作用；不同接口不合成一张图，也不用一张图的 `alt` 代替各接口流程。
- 筛选范围、参数处理、排序与分页、名称回显、失败结果等独立规则较多时，用本接口内的编号列表；共用规则可引用已定义内容。复杂判断按需补核心伪代码；关键查询按 [SQL 与性能检查](sql-review.md) 给出适用的参数化伪 SQL、影响行数与索引依据。不要把不同接口的逻辑连成密集长段。

## 实施与验证

- 说明影响范围：新增/修改的入口与调用方、DTO/VO、业务规则、权限、数据库、缓存、外部副作用及预计文件；对相关旁路分别判断需同步修改、已核实不受影响或待核实。
- 评估契约兼容、参数边界、状态冲突、重复请求及数据影响等实际风险；将未确定的业务规则、字段或外部依赖列为疑问，标明推荐口径及其影响。风险和疑问均需评估，不为填表编造内容。
- 将接口契约映射到 Controller、DTO/VO、Service、数据访问及权限的必要改动，说明是否需要发布 SQL 或真实数据操作；编写代码与在真实环境调用接口分别标注。
- 验证请求与响应字段、成功/失败和关键边界；有分页、并发、重试或副作用时覆盖相应路径。核对同一业务规则的其他入口，交付时列出实际契约与事前方案的差异。
