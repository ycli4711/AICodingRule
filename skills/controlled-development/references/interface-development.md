# 接口开发方案

适用于新增接口，或修改 URL、请求、响应、权限及可见行为的接口。先核对原型、调用方、项目路由和响应包装约定；尚无证据的字段或规则标为待定，不把建议写成已确认契约。

## 接口契约

- 逐个列出接口的 URL、请求方式、用途、调用方、鉴权/数据权限和与现有接口的关系。多个接口可先用总表，但不能遗漏任何新增或变化的入口。
- 对新增接口列出请求字段及响应字段的名称、类型、必填性、默认值、枚举/取值约束和含义；说明分页、排序、ID、日期和响应包装。修改接口时突出变更前后差异、旧调用方兼容方式和错误结果。未变化的共享 DTO 可引用现有契约，不重复整表。
- 明确成功、参数错误、无权限、对象不存在、状态冲突等实际适用的响应；错误码与消息遵循项目约定，不凭空定义。

实施前方案按下列顺序展示，不用一段概述代替字段定义：

1. 接口清单表：`URL | 请求方式 | 用途 | 权限 | 请求/响应对象`。页面 URL 与服务端 API URL 分别写，不能互相代替。
2. 请求字段表：`位置/层级 | 字段 | 类型 | 必填/默认 | 规则与含义`；说明 query、path、body 的实际位置。使用 `PageParams` 等通用包装时，核实并列出外层分页字段和内层业务筛选字段，给出符合项目结构的 JSON 请求示例，不能只写类名。
3. 响应字段表：`字段路径 | 类型 | 可空/取值 | 含义/来源`；每个实际返回字段单独一行，用 `data.records[].字段` 等路径区分包装、分页元数据和列表行。共用包装可引用现有契约并简列关键层级，但本接口新增或供页面使用的列表字段须逐项列明，不能用顿号串联字段名或只写泛型返回类型。
4. 实际适用的错误结果、兼容方式及待定字段。未确认项标“待定”及影响，不留空让读者猜测。

发出实施确认前逐项核对：接口清单中请求方式是否明确；请求字段表与 JSON 示例能否说明客户端实际怎样传值；响应字段表是否让每个页面使用的字段都能查到类型、可空性和来源。缺任一项时补全；确实无法核实时列出具体待定点与所需证据，先澄清受影响契约，不以“按现有约定”代替字段定义。

## 业务时序

- 在实施前给出至少一张核心 Mermaid 时序图，展示调用方、入口、业务层、数据库及实际涉及的外部服务；标出关键校验、状态改变、事务提交、失败返回和外部副作用。只出现于该接口的参与者才入图。
- 多个接口共享相同流程时合并一张图，并在契约表中注明适用接口；独立状态变化或外部副作用另画流程。图表达业务顺序，不以类名和方法名堆满节点。
- 关键判断、事务或重试仅靠图说不清时补核心伪代码；涉及数据库访问时按 [SQL 与性能检查](sql-review.md) 给出适用的参数化伪 SQL、影响行数及索引依据。分页筛选须展示关键 WHERE、ORDER BY、分页及计数口径。简单单行 CRUD 不为填模板编造分支或外部调用。
- 时序图后以“核心逻辑”编号列表分开写筛选范围、参数处理、排序与分页、字典/名称回显、失败结果；只列实际适用项。关键查询用独立的伪 SQL 代码块展示，索引依据和未经验证的性能结论另列。不要把这些内容连成一段密集文字，也不要用行内 SQL 片段代替需要审查的查询结构。

## 实施与验证

- 说明影响范围：新增/修改的入口与调用方、DTO/VO、业务规则、权限、数据库、缓存、外部副作用及预计文件；对相关旁路分别判断需同步修改、已核实不受影响或待核实。
- 评估契约兼容、参数边界、状态冲突、重复请求及数据影响等实际风险；将未确定的业务规则、字段或外部依赖列为疑问，标明推荐口径及其影响。风险和疑问均需评估，不为填表编造内容。
- 将接口契约映射到 Controller、DTO/VO、Service、数据访问及权限的必要改动，说明是否需要发布 SQL 或真实数据操作；编写代码与在真实环境调用接口分别标注。
- 验证请求与响应字段、成功/失败和关键边界；有分页、并发、重试或副作用时覆盖相应路径。核对同一业务规则的其他入口，交付时列出实际契约与事前方案的差异。
