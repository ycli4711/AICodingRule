# 伪 SQL、索引和性能检查

## 先取得事实

从项目代码、迁移或已配置的只读数据库工具核查数据库种类、表结构、主键/唯一约束、索引列顺序、字段类型、租户隔离和软删除规则。数据库无法访问时说明代码中的结构定义可能与实际部署不同。

按风险核实数据规模、基数、请求频率和返回规模；没有证据就标注假设，不能承诺“性能没问题”。使用当前数据库版本的官方资料解决不确定的语法和优化器行为。

## 写出可审查的访问

- 给出参数化伪 SQL，保留真实筛选、关联、排序、分页和批量边界。示意字段明确标注，禁止把用户输入拼进可执行 SQL。
- 每条写入说明环境/租户、筛选条件、字段原值与目标值或计算规则、预期及允许影响行数。批量更新必须明确范围；“全部”只能来自已确认业务范围。
- 行数判断结合驱动的匹配行/实际变更行语义及幂等行为；不能统一认为返回 0 就失败。
- 涉及状态变更时展示合法前置状态及冲突行为；按实际风险选择条件更新、版本号或锁，不机械对所有查询加锁。
- 说明事务和锁的范围、锁持有时长及必要锁顺序；外部网络调用不放在数据库事务内。提交后外部动作失败的重试/一致性机制需与业务要求对齐，不自动引入新架构。

## 查询结构偏好

- 尽量避免子查询，包括相关子查询、标量子查询、派生表以及 IN/EXISTS 中的嵌套 SELECT；先评估简单查询、少量表 JOIN 或多条批量 SQL。不要仅将嵌套查询换成 CTE 就声称已简化。
- 单条 JOIN 查询参与关联的表尽量不超过 3 张，包含主表，即通常最多 2 个 JOIN；同一表以不同别名自关联时按各次参与计算，不通过视图或派生表隐藏实际关联复杂度。
- 超过 3 张表时，优先评估拆成多条 SQL：查询目标主记录和必要关联键，再按键批量读取关联数据，在应用层组装。给出拆分顺序、每条 SQL 的范围、预计查询次数和合并规则，避免逐行查询形成 N+1；键集合较大时明确分批边界。
- 拆分必须保持原业务语义，核对关联条件参与的筛选、排序、分页、总数、去重、聚合、空关联及一对多关系。不能先对未满足完整筛选条件的主表分页，再在应用层过滤而改变结果；也不能用无限制全量读取代替复杂 SQL。
- 说明多次查询之间并发变化的一致性要求，并比较数据库往返、传输量、应用内存与索引访问成本。拆分不是性能更优的证明，不机械增加事务或锁。
- 以上是优先选择，不是绝对禁令。确需子查询或超过 3 张表的 JOIN 时，在实施前说明具体原因、拆分方案的不足，以及结构/执行计划等可用依据；缺少性能证据时明确未验证，不把猜测写成结论。按已有授权处理，不因技术例外重复索取确认。

## 索引与查询成本

- 将 WHERE/JOIN/ORDER BY 的访问模式映射到已有索引；考虑联合索引列顺序、范围条件、排序和选择性。新增索引必须解释既有索引为何不足，以及写入、存储、维护代价。
- 主键等值定位通常无需为附加状态条件增加联合索引；不能仅凭 WHERE 出现某字段就创建索引，也不能假设低基数字段在任何场景都无价值。
- 检查循环查询/N+1、无界结果、无必要的 SELECT *、深分页、重复 COUNT、大 IN 列表及关联放大。根据实际规模决定是否优化，避免一律重写。
- 检查隐式类型转换、索引列函数计算、LIKE 模式等可能影响索引使用的条件。软删除和租户条件必须与实际隔离架构一致；租户独立库不得凭空增加 tenant_id。
- 大表索引/结构变更说明执行与锁风险，区分生成迁移与执行迁移，遵循项目授权，不直接在真实库试运行。

## 最小充分验证

1. 对比最终 ORM/查询构造器生成 SQL 与伪 SQL，确认绑定参数、筛选范围、分页和批量行为；检查不会漏掉模型事件和关联副作用。
2. 主键单行操作可用结构证据和针对性验证；复杂、高频或大数据查询在合适环境检查执行计划，关注访问路径、估算/实际行数、循环次数及排序等成本。
3. EXPLAIN ANALYZE 等工具可能实际执行语句；先核实数据库语义和环境，不能把它当成无副作用只读预览，不能对真实写语句未经授权运行。
4. 模拟测试、SQLite 测试或小数据测试不能证明目标数据库的大规模性能；单纯“使用了索引”也不是性能验收结论。明确缺少的数据、计划或测量。
