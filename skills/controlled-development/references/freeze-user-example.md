# 示例：冻结用户接口

本例为对齐模板。表名、状态值、权限和会话策略均为假设，不可直接作为真实项目实现要求。

## 先核查再对齐

检查现有状态字段、合法状态转换、管理员权限、登录/令牌鉴权入口、用户缓存、审计记录和租户隔离。

待对齐的业务选择：冻结限制哪些操作；已有会话何时受限；订单/退款是否继续；哪些用户允许被冻结；是否允许解冻。本例不因开发冻结接口自动增加解冻功能。

以下假设用户已经确认：禁止新登录及后续受保护请求，订单退款不变，重复冻结不重复记录状态变更；只开发接口并使用隔离测试数据，不冻结真实用户。

## 业务步骤与伪代码

```text
校验管理员权限、租户上下文、用户 ID 和原因
开始事务
    根据主键读取并锁定目标用户
    不存在：返回不存在
    已冻结：返回已冻结，不重复写状态变更日志
    非允许的前置状态：返回冲突
    条件更新状态为冻结
    写入包含原状态、新状态、操作人和原因的审计记录
提交事务
返回冻结成功

新登录和每次受保护请求：根据已对齐的权威状态检查冻结状态
```

“每次请求受限”必须有真实鉴权依据：若已有鉴权读取缓存，方案必须明确缓存失效失败和其他入口如何处理；不能仅写“清缓存”就承诺立即生效。选择数据库检查、会话撤销或既有一致性机制要基于项目证据与业务要求，本例不预选技术方案。

## 伪 SQL

假设当前已切换正确的租户独立数据库，id 是主键，未涉及额外软删除条件；真实项目需补齐实际约束。

```sql
BEGIN;

-- 预期读取 0 或 1 行；应用层处理不存在、已冻结和非法状态
SELECT id, status
FROM t_user
WHERE id = :user_id
FOR UPDATE;

-- 从允许的非冻结状态变为冻结，预期更新 1 行
UPDATE t_user
SET status = :frozen_status,
    updated_time = :now
WHERE id = :user_id
  AND status = :expected_status;

-- 行数异常则回滚，不写成功审计
INSERT INTO t_user_operation_log (
    user_id, operator_id, action,
    before_status, after_status, reason, created_time
) VALUES (
    :user_id, :operator_id, :freeze_action,
    :expected_status, :frozen_status, :reason, :now
);

COMMIT;
```

主键定位最多一行，本例无依据新增 (id, status) 索引。审计表索引根据真实查询访问模式另行评估，不为本次 INSERT 凭空加索引。事务中无外部请求。

## 最小验证与交付

验证无权限、目标不存在、非法前置状态、首次冻结、重复冻结、审计写入失败回滚、新登录和已有会话；多租户及并发入口存在时覆盖隔离和重复操作结果。

交付分别说明代码实现、隔离测试、实际数据操作及未验证环境。没有实际运行测试不能写“测试通过”；不运行批量冻结命令作为验证。
