# 业务 Bug 方案

适用于修复现有行为与已确认业务规则不一致的问题。局部且行为明确的小 Bug 可简述目标、影响与验证；涉及多入口、状态、副作用或契约时再展开。

## 定位与目标

- 给出可复现的当前结果、预期结果和证据，区分用户描述、代码事实及尚未验证的推断。
- 复杂 Bug 在方案中按 `现象与证据 → 根因及影响链 → 修复行为 → 回归验证` 分成独立条目；多个独立入口逐项说明当前、预期及处理方式。不要用“修复相关逻辑”替代根因或修复边界。局部且行为明确的小 Bug 仍可简述。
- 沿实际链路定位直接原因、写入点、消费方和等价入口；说明哪些入口需同步修复，哪些明确不受影响。不要把报错位置直接当作修改边界。

## 修复与验证

- 说明最小必要的行为变化、影响状态/数据、副作用和失败结果；保留现有契约时明确指出。若需要新增或修改接口契约，同时读取 [接口开发](interface-development.md)；涉及数据访问或结构变更时读取 [SQL 与性能检查](sql-review.md)。
- 跨模块、异步或副作用顺序影响根因时，用时序图展示关键差异；复杂判断补核心伪代码。局部且行为明确的小 Bug 不为填模板画图。
- 列出受影响入口、接口、数据、权限、调用方和预计文件，判断每个相关入口需修改、已核实不受影响或待核实；评估历史数据、兼容性、重复执行、并发及外部副作用。需业务决定的口径单列疑问。
- 验证原问题、成功路径、失败路径和关键边界；若有重试、并发或幂等风险再覆盖相应行为。交付核对根因、实际改动及未修复的相关入口。
- 复杂 Bug 请求实施确认前核对根因是否有证据、修复范围是否覆盖已发现的相关入口、回归项是否对应原问题和副作用；无法确认根因时明确假设与下一步只读核查，不把推断写成确定的修复方案。
